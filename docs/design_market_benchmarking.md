# Design-doc: мультиисточниковый бенчмаркинг вознаграждений

**Статус:** ✅ Фаза 0 (дизайн) закрыта — все 7 вопросов отвечены (2026-08-31). Можно начинать Фазу 1. Первый реальный файл-выгрузку (B1 или Job Farovon) хорошо бы получить до старта, чтобы проверить импортёр, но это не блокирует.
**Дата:** 2026-08-31
**Автор:** C&B + разработка
**Связано с:** `docs/Архитектура_и_Требования_Обзор_Рынка.md`, `src/db/schema.sql`, `src/services/analyticsService.js`

---

## 1. Контекст и цель

Сейчас система собирает **только внутренние точечные наблюдения**: HR BP / ответственные вносят по каждому подразделению зарплаты и льготы конкретных компаний-конкурентов (`surveys` — одна строка = одна компания × одна должность). Дашборд строит по ним вилки Min/P25/Median/P75/Max и гэп «Фаровон к рынку».

**Целевое состояние:** система становится платформой сравнения по нескольким источникам данных для одной должности:

| Источник | Природа данных | Пример |
|---|---|---|
| Внутренний сбор (есть сейчас) | точечные наблюдения по компаниям | «ТСЕЛЛ, Руководитель, 5000–10000 сомони» |
| Джоб-сайты (hh и подобные), массово | агрегаты: перцентили, размер выборки, регион, дата | «Бухгалтер, Душанбе, P25=X, P50=Y, P75=Z, N=140, авг-2026» |
| Платные провайдеры (B1, Antal, …) | структурированные обзоры по своим грейдам/кодам, base / total cash / total remuneration по перцентилям, разрезы по отрасли/выручке/географии | «B1 Salary Survey 2026, grade M2, P50 total cash = …» |

C&B-аналитик по одной должности видит: наш оклад vs медиана джоб-сайтов vs P50 B1 vs P50 Antal, с приведением к общей валюте, периоду и дате, и с гэпом.

## 2. Термины

- **Наблюдение (observation)** — одна точка данных: либо *точечная* (одна компания, одно значение), либо *агрегат* (распределение: перцентили + N).
- **Датасет (dataset)** — одна загрузка из одного источника: «B1 Salary Survey 2026», «Выгрузка hh за август 2026». Имеет провайдера, дату отчёта, дату актуальности данных, методологию, лицензию.
- **Позиция-эталон** — должность из справочника Фаровона (`dictionary_positions`).
- **Позиция источника** — должность/код в таксономии источника (у B1/Antal — их грейд/код).
- **Маппинг** — связь «позиция-эталон ↔ позиция источника».
- **Компонент вознаграждения** — base salary (оклад) / total cash (оклад + переменная) / total remuneration (совокупный доход с льготами).

## 3. Ответы на 7 вопросов (от C&B, 2026-08-31)

### 3.1. Формат по источникам — ✅
- **B1** — Excel, **один лист, в нём все должности** (строки = должности, столбцы = перцентили/разрезы). Плоская таблица → простой парсер.
- **Antal** — только **PDF**. Excel не дадут (лицензия, доп. плата). → **не парсим PDF автоматически.** C&B вносит цифры Antal через форму / вставку таблицы в нашем интерфейсе. Данных немного: ~300 должностей × несколько перцентильных столбцов, раз в год.
- **«Job Farovon»** — **наш сайт**, в нём есть функция выгрузки (формат ещё не зафиксирован). → парсить HTML не нужно; берём CSV/Excel-выгрузку, столбцы сопоставляем при первом импорте. Позже (Фаза 3+) — возможна прямая интеграция: Job Farovon сам шлёт данные в `/api/benchmarks/import` по расписанию, раз в год. Данные = вакансии → скорее всего сырьё, режим «сырьё → считаем перцентили».

### 3.2. Периодичность — ✅ раз в год
Каждый источник обновляется ежегодно. → тяжёлый инкрементальный пайплайн не нужен; храним историю датасетов по годам для тренда «год к году».

### 3.3. Грейды — ✅ пока нет
Систему грейдов ещё не приняли. Планируется **грейдирование Korn Ferry, только для верхних уровней должностей**. →
- Сейчас маппинг **по названию должности** (наша ↔ должность источника).
- Модель сразу закладывает поле `grade` и справочник систем грейдов; когда KF-грейды появятся у топ-должностей — по ним маппинг идёт через грейд, для остальных остаётся по названию.

### 3.4. Сырьё или перцентили — ✅
- **B1, Antal** — «уже готовые», т.е. **перцентили** (P25/P50/P75 ± P10/P90) + N. Свой расчёт не нужен.
- **Job Farovon** — вероятно **сырьё** (список вакансий с вилками); перцентили считаем сами. Подтвердится на первой выгрузке.
- Модель поддерживает оба режима: `stat_type = point` (сырьё, наш расчёт перцентилей) и `stat_type = p25/p50/…` (готовый агрегат).

### 3.5. Объём — ✅
**300+ уникальных должностей-эталонов**, строк в датасетах — больше (разрезы: регион/отрасль/грейд). Для Turso/SQLite объём комфортный.

### 3.6. Кто видит платные данные — ✅ только C&B / Admin
Весь раздел бенчмаркинга (не только B1/Antal) на старте доступен **только ролям C&B и admin**. `benchmarks:view_licensed` оставляем в модели на будущее — если позже HR BP дадут просмотр несекретных источников.

### 3.7. Роль внутреннего сбора — ✅ остаётся
Ручной сбор HR BP по подразделениям (`surveys`) **остаётся как есть** — равноправный источник рядом с Job Farovon / B1 / Antal. Экран сбора не трогаем; в сравнении по должности «внутренний» — одна из колонок.

## 3-бис. Осталось получить (не блокирует старт)

- Реальные файлы-образцы: B1 Excel и выгрузка Job Farovon. Как появятся — проверим импортёр и зафиксируем пресеты столбцов. До тех пор импорт с **настраиваемым сопоставлением столбцов**.

## 4. Модель данных (предложение)

Существующие таблицы (`surveys`, `dictionary_positions`, `divisions`, …) не трогаем — внутренний сбор работает как есть. Добавляем отдельный слой бенчмаркинга.

```
data_sources        1 ──< benchmark_datasets      1 ──< benchmark_rows
(провайдер)               (одна загрузка)                (строки распределений/точек)
                                                          │
dictionary_positions 1 ──< position_map >── source_positions
(наша должность)             (сопоставление)     (должность/код источника)
```

### 4.1. `data_sources` — справочник источников
| поле | тип | описание |
|---|---|---|
| `key` | TEXT PK | `internal`, `jobsite_hh`, `consultancy_b1`, `consultancy_antal`, … |
| `title` | TEXT | «HeadHunter», «B1 Salary Survey», «Antal» |
| `kind` | TEXT | `internal` / `jobsite` / `consultancy` |
| `is_licensed` | INTEGER | 1 = лицензированные данные (доступ ограничен) |
| `default_currency` | TEXT | |
| `notes` | TEXT | методология, ссылка на договор |

### 4.2. `benchmark_datasets` — загрузка
| поле | тип | описание |
|---|---|---|
| `id` | INTEGER PK | |
| `source_key` | TEXT FK → data_sources | |
| `title` | TEXT | «B1 Salary Survey 2026», «hh выгрузка 2026-08» |
| `report_date` | TEXT | дата публикации отчёта |
| `data_as_of` | TEXT | на какую дату актуальны сами данные (для старения) |
| `currency` | TEXT | валюта датасета |
| `methodology` | TEXT | |
| `uploaded_by` | TEXT | |
| `uploaded_at` | DATETIME | |
| `row_count` | INTEGER | |
| `state` | TEXT | `draft` / `active` / `archived` |

### 4.3. `benchmark_rows` — наблюдения
Одна строка = одно наблюдение по одной позиции источника в одном разрезе.

| поле | тип | описание |
|---|---|---|
| `id` | INTEGER PK | |
| `dataset_id` | INTEGER FK | |
| `source_position_id` | INTEGER FK → source_positions | |
| `region` | TEXT | разрез: регион / город |
| `industry` | TEXT | разрез: отрасль (для провайдеров) |
| `company_size` | TEXT | разрез: выручка/численность (для провайдеров) |
| `grade` | TEXT | грейд/уровень в системе источника |
| `component` | TEXT | `base` / `total_cash` / `total_remuneration` |
| `currency` | TEXT | |
| `period` | TEXT | `в месяц` / `в год` (нормализуем при чтении) |
| `stat_type` | TEXT | `point` / `p10` / `p25` / `p50` / `p75` / `p90` / `avg` / `min` / `max` |
| `value` | REAL | |
| `sample_n` | INTEGER | размер выборки (для агрегатов) |
| `company` | TEXT | только для `point`-наблюдений (внутренний сбор) |

> Внутренний сбор можно **не мигрировать**, а на лету проецировать `surveys` в этот же формат (view/адаптер): `component='base'`, `stat_type='point'`, `value = (pay_from+pay_to)/2`. Тогда сервис сравнения работает с одним интерфейсом.

### 4.4. `source_positions` — таксономия источника
| поле | тип | описание |
|---|---|---|
| `id` | INTEGER PK | |
| `source_key` | TEXT FK | |
| `code` | TEXT | код должности/грейда у источника (если есть) |
| `label` | TEXT | название должности у источника |
| `family` | TEXT | функция/семейство (Finance, IT, …) — если источник даёт |

### 4.5. `position_map` — сопоставление
| поле | тип | описание |
|---|---|---|
| `id` | INTEGER PK | |
| `dict_position_id` | INTEGER FK → dictionary_positions | наша должность |
| `source_position_id` | INTEGER FK → source_positions | должность источника |
| `confidence` | TEXT | `exact` / `close` / `approx` |
| `mapped_by` | TEXT | |
| `mapped_at` | DATETIME | |
| `note` | TEXT | почему так сопоставлено |

Одна наша должность может маппиться на несколько позиций разных источников (и наоборот). Уникальность — по паре `(dict_position_id, source_position_id)`.

## 5. Маппинг должностей — критичный узел

Плохой маппинг = мусорные сравнения, поэтому выделено отдельно.

- **Экран маппинга** (админка → «Сопоставление должностей»): слева наши должности, справа — позиции выбранного источника; аналитик связывает, ставит `confidence` и комментарий.
- **Помощь в подборе:** нечёткое совпадение по названию (как уже сделано для `positionCanon` в `surveyImport.js`), подсказка «похожие».
- **Непокрытые должности** видны списком — по ним сравнения не будет, честно показываем «нет данных источника».
- Если C&B принимает систему грейдов провайдера (ответ 3.3) — маппинг идёт через грейд, а не через название: наша должность → грейд → все позиции этого грейда.
- Маппинг **живёт дольше датасета**: новый датасет того же источника переиспользует сопоставления по `code`.

## 6. Нормализация

Всё приводится к общей базе перед сравнением:

1. **Валюта** — таблица курсов `fx_rates(currency, date, rate_to_base)`, база — сомони (или та, что назовёт C&B). Для датасета берём курс на `data_as_of`.
2. **Период** — «в год» → «в месяц» (÷12); ЧТС → «в месяц» (× 168, уже есть в `analyticsService`).
3. **Компонент** — сравниваем одинаковое с одинаковым: base с base, total cash с total cash. Если у источника только total cash, а у нас только base — помечаем несопоставимость, не смешиваем.
4. **Грейд** — если приняли систему грейдов, приводим к ней; иначе сравнение по должности-эталону.
5. **Старение (aging)** — данные разных дат приводим к общей дате отчёта через годовой % движения рынка (параметр, задаёт C&B, можно по функциям/регионам). `value_aged = value × (1 + annual_move)^(months_diff/12)`.

Все коэффициенты (курсы, % старения, часы в месяце) — **настраиваемые параметры**, не хардкод.

## 7. Пайплайн импорта

Раз в год, только C&B, ~300 должностей, реальных файлов пока нет → вместо N жёстких парсеров — **один настраиваемый табличный импортёр**.

**Схема:** загрузка Excel/CSV (или вставка таблицы) → **шаг сопоставления столбцов** → предпросмотр (dry-run) → запись в `benchmark_dataset` (`draft`) → активация. По образцу `surveyImport.js` (dry-run + отчёт о проблемных строках + `dupAction`).

**Шаг сопоставления столбцов:** C&B один раз для источника указывает, какой столбец файла = должность / регион / отрасль / грейд / валюта / период / компонент, и либо столбец сырого значения, либо набор столбцов перцентилей (`p25`, `p50`, `p75`, …) + `N`. Пресет сохраняется на источник и переиспользуется в следующем году.

По источникам:
- **B1** — Excel, один лист, все должности → загрузка файла + пресет столбцов.
- **Job Farovon** — CSV → тот же импортёр; если сырьё, флаг «это отдельные вакансии» → перцентили считаем сами при чтении.
- **Antal** — Excel не дадут. Тот же импортёр в режиме **вставки таблицы**: C&B копирует таблицу из PDF (или набивает вручную) в поле → парсим как CSV. Данных мало (должность × 3–5 перцентилей, раз в год).
- **Внутренний сбор** — не импортируется, проецируется из `surveys` на лету.

**Проблемные строки** не молча пропускаются — отчёт: «нет маппинга должности», «неизвестная валюта», «пустой перцентиль», «должность не из справочника».

Отдельные парсеры под конкретный источник заводим позже, только если реальный файл окажется слишком грязным для табличного импортёра.

## 8. Сервис сравнения и выходы

`benchmarkService.compare({ positionId, region?, industry?, grade?, component?, asOfDate? })`:

1. По `position_map` находит позиции всех источников для этой должности.
2. Тянет `benchmark_rows` активных датасетов + проекцию `surveys`.
3. Нормализует (раздел 6).
4. Отдаёт по каждому источнику: P25 / P50 / P75 (или точку + N), дату, лицензию-флаг.
5. Считает гэп «Фаровон к рынку» по каждому источнику и «сводную рыночную медиану».

**Выходы:**
- Лист сравнения по должности: таблица «источник × перцентиль», гэп, дата данных, размер выборки.
- Сводный отчёт по всем должностям функции/направления.
- Экспорт CSV/Excel (через уже готовый `csvCell` — защита от формул) с журналированием выгрузки (`/api/audit/export` уже есть).
- (позже) тренды: один источник во времени по датасетам.

## 9. Доступ и лицензии

Права (`src/config/capabilities.js`) — добавить ресурс `benchmarks`:

| capability | смысл |
|---|---|
| `benchmarks:view` | видеть сравнение по несекретным источникам (внутренний + джоб-сайты) |
| `benchmarks:view_licensed` | видеть лицензированные источники (B1, Antal) — по умолчанию только C&B/admin |
| `benchmarks:import` | загружать датасеты |
| `benchmarks:map` | сопоставлять должности |

**На старте (ответ 3.6):** весь раздел бенчмаркинга — только роли `cb` и `admin`. Практически это значит: `benchmarks:view` по умолчанию выдаётся только им, `view_licensed` держим в модели для будущего (если HR BP дадут просмотр джоб-сайт-данных).

Роли уже настраиваемые (конструктор ролей) — новые права раздаются через него. Лицензированные данные:
- флаг `data_sources.is_licensed = 1`;
- в `benchmarkService` строки лицензированных источников не попадают в ответ без `benchmarks:view_licensed`;
- в лицензии часто есть лимит на число пользователей и запрет на реэкспорт — зафиксировать в `notes` источника и, если нужно, ограничить экспорт лицензированных данных.

## 10. Влияние на существующую систему

- **БД:** только новые таблицы + `fx_rates` + параметры. `surveys` не трогаем.
- **Backend:** новый модуль `benchmark*` (controller/service/importers/routes), новые capabilities, новые пункты в конструкторе ролей.
- **Frontend:** новый крупный раздел (сравнение + маппинг + импорт датасетов). ⚠️ `public/index.html` уже ~480 КБ одним файлом — добавление целого модуля усилит проблему. **Отдельный вопрос к обсуждению:** не пора ли выделить фронт в модули / ввести сборку. Можно отложить, но заложить в план.
- **Миграции:** идемпотентные, как сейчас (`ensureColumn` / `CREATE TABLE IF NOT EXISTS`).
- **CI:** парсеры покрыть тестами (сейчас `npm test` — заглушка; это первый реальный повод завести тесты).

## 12. Открытые вопросы и риски

- **Маппинг** — самый большой риск по трудозатратам и качеству. Нужен аналитик, который его ведёт.
- **Лицензии платных данных** — юридические ограничения на круг пользователей и реэкспорт; уточнить у C&B до загрузки.
- **Сопоставимость компонентов** — нельзя сравнивать base одного источника с total cash другого; где данных о компоненте нет — не угадывать.
- **Старение и курсы** — расхождение дат источников; параметры движения рынка задаёт C&B, иначе цифры несопоставимы.
- **Размер фронтенда** — один HTML-файл на 480 КБ; новый модуль это обострит.
- **Качество джоб-сайт-данных** — самоотбор вакансий, «зарплата не указана», завышение в объявлениях; помечать достоверность источника (как `trust` в `surveys`).

## 13. Оценка объёма (грубо)

- Фаза 1: ~1.5–2 недели (схема + настраиваемый импортёр + маппинг-экран + лист сравнения + права).
- Фаза 2: ~2–3 недели (2 парсера + разрезы + нормализация + права).
- Фаза 3: ~2 недели.
- Фаза 4: отдельно, по решению.

Итого «до полноценного бенчмаркинга» — порядка 6–8 недель разработки, плюс работа C&B по маппингу параллельно.
