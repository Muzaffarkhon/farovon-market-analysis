## 2. Полный аудит: что ещё не перенесено из старого клиента в новый

Сверили все серверные `/api/*` маршруты с тем, что реально вызывается из `web/`. Список подтверждён построчно (не по памяти).

**Существенное:**
1. **Онбординг нового пользователя** — подтверждение ФИО, выбор своих подразделений, отметка «прошёл онбординг» при первом входе (`/auth/change-name`, `/auth/set-units`, `/auth/onboarded`). В новом клиенте экрана нет вообще.
2. **Живое обновление данных** — старый клиент периодически опрашивает `/live-signature` и сам обновляет экран при изменениях. Новый клиент грузит данные один раз при открытии.
3. **Привязка/отвязка Telegram из профиля** (`/telegram/link`, `/telegram/unlink`, `/telegram/bot-info`) — отсутствует в новом клиенте.

**Административное:**
4. **Конструктор ролей** (`/admin/roles`, `/admin/roles/:key/rename`, `/admin/roles/:key/delete`) — в новом клиенте можно только редактировать права существующих ролей, создать/переименовать/удалить роль нельзя.
5. **Справочники (компании/должности)** — инструмент объединения дублей и переименования записей в общих справочниках (`/admin/dictionary/:kind*`). Не путать со штатным расписанием из 1С — то уже перенесено (`StaffScreen`).
6. **Обслуживание и статус данных** (`/admin/maintenance`, `/admin/data-status`, `/admin/import-survey`) — служебные кнопки «запустить обслуживание», «статус загруженных данных», массовый CSV-импорт анкеты через админку.
7. **Бейдж непрочитанных** в админском инбоксе поддержки (`/admin/support/unread-count`) — сам инбокс работает, просто нет счётчика-уведомления рядом с пунктом меню.
8. **Смежные группы подразделений** (`/admin/divisions/adjacent-group*`) — объединение похожих подразделений (разные площадки одной сети) в одну карточку сравнения зарплат. Отображается в оргструктуре как карточка «Смежная · N площ.», задаётся полем `group_key` у подразделения. Ни отображения, ни редактирования в новом клиенте нет.

**Второстепенное:**
9. **Выгрузка в CSV** — у старого дашборда была кнопка экспорта сырых данных (`/dashboard/export-csv`, `/benchmarks/export`). Выгрузка реестра (`/registry/export`) уже перенесена, эти — нет.
10. **Персональные веса по должности** в бенчмаркинге (`/benchmarks/position-weights`) — сейчас можно менять веса источников целиком, override по одной конкретной должности нельзя.

**Полностью перенесено и работает:** анкета сбора данных, реестр, дашборды (кроме CSV-экспорта), координация, грейдинг с комиссией, риски, бенчмаркинг (кроме двух пунктов выше), поддержка (кроме бейджа), оргструктура (кроме смежных групп), рассылка, журнал изменений.

## 3. Новая функция: «Пересмотр заработной платы»

**Важно:** более ранняя версия этого раздела (первая половина той же сессии) описывала самодельную упрощённую заявку («заявка на изменение зарплаты», права `salary:*`) — оказалось, что в проекте уже был согласованный с заказчиком документ на эту функцию, который тогда не нашли. Та версия **полностью удалена** (код, таблицы `salary_*`, права) и переделана заново по документу. Текст ниже — про финальную, верную версию.

**Спецификация:** [docs/superpowers/specs/2026-09-22-comp-review-design.md](../superpowers/specs/2026-09-22-comp-review-design.md), статус «согласован по ключевым вопросам 22.09.2026». Читать его целиком перед любой доработкой этой функции — здесь только выжимка.

**Маршрут:** Черновик (HRBP) → Проверка C&B (может вернуть на доработку с комментарием) → Согласование HRD (может отклонить всю заявку) → Голосование комиссии **большинством от зафиксированного состава** — пропускается для типа заявки «выход из стажировки» → Кадровик вносит в 1С → Закрыта. Решения C&B/HRD — на уровне всей заявки; решения комиссии — **по каждому сотруднику независимо** (заявка — «опросник» на несколько сотрудников разом, отклонённый выпадает, остальные идут дальше; заявка закрывается, когда по каждому есть финальное решение).

**Ключевые решения, зафиксированные в документе (§9) — не пересматривать без явного запроса:**
1. HRD — конкретный человек (Сатторов Илхомчон Ахмадчонович), не роль системы; право `comp:approve_hrd` выдаётся ему персонально через «Роли и доступы». Ему же можно дополнительно выдать `comp:vote` — тогда он и голосует в комиссии.
2. Режим голосования комиссии переключаемый (открытое — голоса видны сразу; закрытое — видно только «проголосовал/нет» до итога) — настройка в «Администрирование → Пересмотр ЗП — комиссия», действует на новые заявки.
3. Большинство считается **от состава комиссии**, не от числа проголосовавших. Состав фиксируется («снимок») в момент, когда HRD передаёт заявку в комиссию (колонка `comp_requests.committee_snapshot`, JSON-список логинов) — более поздние изменения живого списка `comp_committee_members` на уже идущее голосование не влияют. Не проголосовавшие видны C&B/администратору всегда, независимо от режима; кнопка «Напомнить» — вручную (C&B/админ) и автоматически раз в 3 дня без движения — через уже существующий ежедневный Vercel Cron (`vercel.json` → `/api/cron/reminders`), не отдельный крон.

**Правило 6 месяцев (§2):** без истории пересмотров — всегда можно; меньше 6 месяцев с последнего — только с кодом основания «удержание/контр-оффер» или «уникальный случай» и обязательным текстом обоснования, иначе система отказывает при добавлении сотрудника в черновик.

**Данные:** `dictionary_positions.pay_from/pay_to` — источник «вилки» для положения оклада в вилке (compa-position); `benchmarkService.compare()` — источник рыночной медианы для compa-ratio на шаге C&B (если сопоставления с бенчмаркингом нет — поле остаётся пустым, C&B заполняет вручную). «Текущий оклад» сотрудника — не колонка на `staff_directory` (та целиком пересоздаётся при каждом импорте из 1С), а последняя запись в новой таблице `comp_review_history` по паре `(unit, fio)`, которая переживает реимпорт; туда же пишется история для правила 6 месяцев.

**Осознанно не сделано (нужна внешняя инфраструктура/решение):**
- **Вложения файлов** (документ-основание, до 5 файлов, PDF/фото) — по документу должны храниться в Vercel Blob, которого в проекте нет. Поле `basis_document` пока текстовое (ссылка/название вручную), самой загрузки файлов нет.

**Что сделано:**
- Backend: 8 новых таблиц (`comp_requests`, `comp_request_employees`, `comp_variable_pay`, `comp_variable_pay_kinds`, `comp_committee_members`, `comp_committee_votes`, `comp_settings`, `comp_activity`, `comp_review_history`) в `src/db/migrate.js` (миграция `createCompReview`, дропает старые `salary_*`); чистая бизнес-логика (правило 6 месяцев, рост/compa-ratio/вилка, итог голосования большинством от снимка состава) в `src/services/compReviewLogic.js` — 13 юнит-тестов в `test/compReviewLogic.test.js`, без БД; БД-слой в `src/services/compReviewService.js`; контроллер `src/controllers/compReviewController.js`; маршруты `/api/comp/*`. 6 новых прав (`comp:submit/review_cb/approve_hrd/vote/payroll/admin`) в `capabilities.js` — `comp:submit`+`comp:review_cb` по умолчанию у роли `cb`, `comp:submit` у `hrbp`, остальные — только персонально. Полный сквозной прогон через сервисный слой (черновик → все этапы → закрытие, обе ветки — с комиссией и без) сделан вручную в этой сессии, багов найдено и исправлено два (см. код).
- Новый клиент (`web/`): пункт «Пересмотр ЗП» в меню; реестр с вкладками «Ждут меня / Мои / Все актуальные / Закрытые» (`web/src/features/compReview/RequestsListScreen.tsx`); экран заявки с карточками сотрудников, действиями по каждому этапу и лентой событий/комментариев (`RequestScreen.tsx`, `EmployeeCard.tsx`, `EmployeeAddForm.tsx`); админский экран состава комиссии и режима голосования (`web/src/features/admin/compReview/CompCommitteeScreen.tsx`).
- Таблица сотрудников заявки в ТЗ описана как «опросник» (сотрудники колонками, поле — строка, кнопка «→ скопировать вправо во все»). Сделано вертикальным списком карточек — тот же набор полей и действий, но не построчная сетка и без кнопки копирования между сотрудниками. Функционально эквивалентно, визуально отличается от вайрфрейма в документе.

**Открытое:**
- Тот же нюанс с видимостью в меню, что раньше — пункт меню требует хотя бы одного из прав `comp:*`, чистое членство в комиссии (без права) его не даёт. При добавлении члена комиссии — выдать ему `comp:vote` через «Роли и доступы», иначе он не увидит раздел (хотя голосовать технически сможет по прямой ссылке).
- Файлы-вложения — см. выше, нужно решение по Vercel Blob.
- Прод-QA не делали — только автотесты, ручной сквозной прогон через сервисный слой и сборка.
