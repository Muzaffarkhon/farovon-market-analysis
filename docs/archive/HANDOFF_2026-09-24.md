## 2. Полный аудит: что ещё не перенесено из старого клиента в новый

Сверили все серверные `/api/*` маршруты с тем, что реально вызывается из `web/`. Список подтверждён построчно (не по памяти).

**Существенное:**
1. **Онбординг нового пользователя** — подтверждение ФИО, выбор своих подразделений, отметка «прошёл онбординг» при первом входе (`/auth/change-name`, `/auth/set-units`, `/auth/onboarded`). В новом клиенте экрана нет вообще.
2. **Живое обновление данных** — старый клиент периодически опрашивает `/live-signature` и сам обновляет экран при изменениях. Новый клиент грузит данные один раз при открытии.
3. **Привязка/отвязка Telegram из профиля** (`/telegram/link`, `/telegram/unlink`, `/telegram/bot-info`) — отсутствует в новом клиенте.

**Административное:**
4. **Конструктор ролей** (`/admin/roles`, `/admin/roles/:key/rename`, `/admin/roles/:key/delete`) — в новом клиенте можно только редактировать права существующих ролей, создать/переименовать/удалить роль нельзя.
5. **Справочники (компании/должности)** — инструмент объединения дублей и переименования записей в общих справочниках (`/admin/dictionary/:kind*`). Не путать со штатным расписанием из 1С — то уже перенесено (`StaffScreen`).
6. **Обслуживание и статус данных** (`/admin/maintenance`, `/admin/data-status`, `/admin/import-survey`) — служебные кнопки «запустить обслуживание», «статус загруженных данных», массовый CSV-импорт анкеты через админку.
7. **Бейдж непрочитанных** в админском инбоксе поддержки (`/admin/support/unread-count`) — сам инбокс работает, просто нет счётчика-уведомления рядом с пунктом меню.
8. **Смежные группы подразделений** (`/admin/divisions/adjacent-group*`) — объединение похожих подразделений (разные площадки одной сети) в одну карточку сравнения зарплат. Отображается в оргструктуре как карточка «Смежная · N площ.», задаётся полем `group_key` у подразделения. Ни отображения, ни редактирования в новом клиенте нет.

**Второстепенное:**
9. **Выгрузка в CSV** — у старого дашборда была кнопка экспорта сырых данных (`/dashboard/export-csv`, `/benchmarks/export`). Выгрузка реестра (`/registry/export`) уже перенесена, эти — нет.
10. **Персональные веса по должности** в бенчмаркинге (`/benchmarks/position-weights`) — сейчас можно менять веса источников целиком, override по одной конкретной должности нельзя.

**Полностью перенесено и работает:** анкета сбора данных, реестр, дашборды (кроме CSV-экспорта), координация, грейдинг с комиссией, риски, бенчмаркинг (кроме двух пунктов выше), поддержка (кроме бейджа), оргструктура (кроме смежных групп), рассылка, журнал изменений.

## 3. Новая функция: «Заявка на изменение зарплаты»

В проекте раньше не было нигде — ни в коде, ни в старом клиенте. Собрали требования с нуля в этой сессии, реализовали backend + новый клиент полностью, backend-тестами и frontend-тестами покрыто.

**Как работает (решения зафиксированы, не пересматривать без явного запроса):**
- Инициирует HR BP (право `salary:request`, по умолчанию есть у роли `hrbp`).
- Цепочка согласования: **менеджер отдела C&B → HRD → комиссия**. «Менеджер C&B» и HRD — не роли системы (`ROLES` в `capabilities.js` фиксирован: admin/cb/hrbp/dir_head/head/user), это отдельные права (`salary:approve_cb`, `salary:approve_hrd`), выдаются конкретным людям персонально через «Роли и доступы» — так же, как HRD не привязан ни к одной из существующих ролей.
- Комиссия (`salary:committee` — управляет составом; голосовать может любой, кто добавлен в список, без отдельного права) решает **единогласно**: любой отказ сразу отклоняет заявку, не дожидаясь остальных. Состав — глобальный список 3–4 человек, не по блокам (в отличие от комиссии грейдинга). Управляется в «Администрирование → Заявки на зарплату — комиссия».
- Сумма — суммой **или** процентом от текущего оклада (оба варианта в форме, взаимоисключающие).
- Основание — чек-листом (переход на должность / выход из стажировки / индивидуальный подход / бенчмаркинг / грейдинг / «другое» с обязательным текстом), можно несколько сразу.
- После финального одобрения комиссией — записывается в `salary_history` (новая таблица) и это становится «текущим окладом» сотрудника.

**Важная техническая деталь:** `staff_directory` (справочник сотрудников) **целиком пересоздаётся** при каждом импорте штата из 1С (`DELETE FROM staff_directory` + вставка заново) — хранить «текущий оклад» отдельной колонкой на этой таблице нельзя, обнулился бы при следующей загрузке. Вместо этого текущий оклад — всегда последняя запись в `salary_history` по паре `(unit, fio)`, которая переживает любой реимпорт.

**Что сделано:**
- Backend: 4 новые таблицы (`salary_requests`, `salary_request_decisions`, `salary_committee_members`, `salary_history`) в `src/db/migrate.js`; чистая бизнес-логика вынесена в `src/services/salaryRequestLogic.js` (без БД, юнит-тестируется напрямую — 13 тестов в `test/salaryRequestLogic.test.js`); БД-слой в `src/services/salaryRequestService.js`; контроллер `src/controllers/salaryRequestController.js`; маршруты `/api/salary/*`. 5 новых прав в `capabilities.js`.
- Новый клиент (`web/`): раздел «Заявки на зарплату» в левом меню (виден всем с любым из прав на заявки) — вкладки «Новая заявка» (если есть право), «На согласовании — <шаг>» (по одной на каждый шаг, доступный пользователю), «История окладов» (видна всем, кто попал в раздел). Плюс админский экран управления комиссией. Всё в `web/src/features/salary/` и `web/src/features/admin/salary/`.

**Открытое:**
- **Нюанс видимости в меню**: пункт «Заявки на зарплату» показывается по наличию прав (`salary:request`/`salary:approve_cb`/`salary:approve_hrd`/`salary:committee`/`salary:view`) — обычным способом, как и весь остальной интерфейс. Но право голосовать в комиссии не требует отдельного права (`salary:committee` — это право на управление составом, не на голосование) — то есть человека можно добавить в комиссию, а пункт меню он не увидит, пока ему не выдать ещё и `salary:view` (или любое другое из списка) отдельно через «Роли и доступы». Это осознанный компромисс — не стали давать право `salary:committee` голосующим членам, чтобы не путать «состою в комиссии» с «управляю составом комиссии». При первом реальном использовании не забыть выдать `salary:view` всем трём-четырём членам комиссии вручную.
- Никакого прод-QA не делали — только тесты и сборка.
- Не решён вопрос уведомлений (Telegram/рассылка) о новой заявке, ожидающей решения — сейчас узнать о ней можно только зайдя в раздел самому.
