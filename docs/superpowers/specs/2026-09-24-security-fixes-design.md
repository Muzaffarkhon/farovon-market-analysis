## 2. CSRF — двойная отправка токена

### 2.1 Почему именно так

Сессия принимается из `httpOnly`-куки `farovon_session`
(`authController.js:83-91`, `sameSite: 'lax'`) **или** из заголовка
`Authorization`/`X-Token` (для Telegram Mini App — куки не всегда
доступны во фрейме `web.telegram.org`, `auth.js:19-27`). Токен в
заголовке подделать межсайтовым запросом нельзя (атакующая страница не
может произвольно проставить заголовок на чужой запрос без CORS-preflight,
который сервер отклонит) — значит CSRF-проверка нужна **только** для
запросов, аутentифицированных именно кукой.

### 2.2 Механизм — double-submit cookie

При установке сессии (`login`, `resume`, `telegramLogin`, смена пароля)
сервер ставит **вторую** куку — `farovon_csrf`, случайный токен,
**не** `httpOnly` (её должен прочитать JS, это и есть суть механизма),
`sameSite: 'lax'`, тот же `maxAge`, что у сессии. Каждый
изменяющий запрос (`POST`/`PUT`/`PATCH`/`DELETE`), аутентифицированный
кукой (нет заголовка `Authorization`/`X-Token`), обязан прислать
заголовок `X-CSRF-Token` со значением, совпадающим с кукой. Атакующая
страница может заставить браузер отправить куку автоматически, но не
может её прочитать (не её origin) и подставить в заголовок — запрос
отклоняется.

### 2.3 Сервер

`src/middleware/csrf.js` (новый):

```js
function csrfProtect(req, res, next) {
  if (!['POST', 'PUT', 'PATCH', 'DELETE'].includes(req.method)) return next();
  const authHeader = req.headers['authorization'] || req.headers['x-token'];
  if (authHeader) return next(); // токен в заголовке — не кука, CSRF не грозит

  const m = /(?:^|;\s*)farovon_csrf=([^;]+)/.exec(req.headers.cookie || '');
  const cookieToken = m ? decodeURIComponent(m[1]) : null;
  const headerToken = req.headers['x-csrf-token'];
  if (!cookieToken || !headerToken || cookieToken !== headerToken) {
    return res.status(403).json({ ok: false, error: 'CSRF_TOKEN_MISMATCH', message: 'Обновите страницу и попробуйте снова' });
  }
  next();
}
```

Подключается в `src/routes/api.js` после `authMiddleware`, **до**
маршрутов, с явным исключением для публичных/секрет-защищённых путей,
которые не используют куку сессии вовсе: `/auth/login`, `/auth/telegram`,
`/auth/logout`, `/telegram/webhook`, `/cron/reminders` (все уже защищены
собственным механизмом — пароль/подпись/секрет — а логин-CSRF низкой
серьёзности: максимум, что даёт форс-логин чужим POST — залогинить
жертву под чужим аккаунтом, не более, а тут даже это невозможно без
знания пароля).

`setSessionCookie` (`authController.js:83`) — рядом ставит
`farovon_csrf`:

```js
function setCsrfCookie(res) {
  const token = crypto.randomBytes(24).toString('hex');
  res.cookie('farovon_csrf', token, {
    httpOnly: false, secure: config.nodeEnv === 'production',
    sameSite: 'lax', maxAge: 7 * 24 * 60 * 60 * 1000, path: '/'
  });
}
```

Вызывается везде, где сейчас вызывается `setSessionCookie` (4 места:
`login`, `resume`, `telegramLogin`, смена пароля с ре-логином).

### 2.3 Клиент

Оба клиента читают куку `farovon_csrf` из `document.cookie` и
проставляют `X-CSRF-Token` на каждый мутирующий запрос:

- **Новый клиент** — `web/src/api/client.ts`, функция `request()`:
  если `method !== 'GET'`, добавить заголовок из значения куки.
- **Старый клиент** — общая функция `call()` (`client/app-core.js`),
  та же логика.

Запрос без токена (например, старая открытая вкладка до обновления
кода) получит 403 с понятным сообщением — не поломка молча, а
подсказка обновить страницу.

## 3. CSP — без `unsafe-inline` для `/new/*`

Старый клиент (`client/`) держит инлайн-обработчики
(`onclick=`) и ручную сборку разметки — `unsafe-inline` ему нужен,
не трогаем. Новый клиент (`web/src`) — ноль инлайн-обработчиков (JSX
экранирует по умолчанию), может работать без него уже сегодня.

`src/server.js:133-156` — CSP сейчас ставится глобально одним
`helmet`-вызовом. Разделяем: второй, более строгий набор директив
(без `unsafe-inline` в `script-src`/`script-src-attr`) применяется
только к ответам с `req.path` начинающимся на `/new` — через
собственный `helmet()`-инстанс, подключённый `app.use('/new', ...)`
**до** общего (Express выбирает первый подходящий middleware по пути).

## 4. Права роли C&B — сузить до рабочих функций

Сейчас `DEFAULT_ROLE_CAPABILITIES.cb` — весь каталог `CAPABILITIES`
(`capabilities.js:59`), с комментарием, что это сознательный слепок
поведения «до правки» ради нулевой разницы при миграции. Раз с тех пор
прошло уже 8 этапов редизайна — пора сузить до того, что C&B-аналитик
реально делает.

**Убрать** (управление учётками и массовые рассылки — не функция C&B):
`users:create`, `users:edit`, `broadcast:send`, `service:edit`.

**Оставить всё остальное** — сбор, дашборды, координация, оргструктура,
справочники, период, бенчмаркинг целиком, грейдирование целиком, риски
ключевого персонала, чат поддержки, `users:view` (нужен для пикеров
«назначить ответственного»), `service:view`.

Это только меняет **дефолт для новых сред** (`INSERT OR IGNORE` при
миграции) — уже выданные в проде права строкам `role_capabilities WHERE
role='cb'` не трогает автоматически (мягко: убрать нежелательные строки
отдельным `DELETE`, только если решим синхронизировать прод — отдельный
ручной шаг, не часть кода).

## 5. Мягкое удаление — датасеты бенчмаркинга

Единственное место из пункта 8, где хард-делит **не** защищён проверкой
использования/подтверждением (в отличие от `deleteDivision` — блокирует
удаление при живом использовании, `adminController.js:926-932`, и
`dictionaryController.remove` — двухшаговое подтверждение с отчётом об
объёме, `dictionaryController.js:312-324`): `benchmarkService.
deleteDataset` (`benchmarkService.js:549-556`) — сразу `DELETE FROM
benchmark_rows` + `DELETE FROM benchmark_datasets`, без подтверждения,
без журнала.

`divisions`/справочники не трогаем в этом проходе — они уже достаточно
защищены существующими проверками, риск ниже, чем оценивало ТЗ.

**Правка:** `ensureColumn('benchmark_datasets', 'archived_at',
'DATETIME')`. `deleteDataset(id)` → `UPDATE benchmark_datasets SET
archived_at = CURRENT_TIMESTAMP WHERE id = ?` вместо `DELETE`; списки
датасетов (`listDatasets` и т.п.) — добавить `WHERE archived_at IS
NULL`. Запись в `audit_log` (сейчас её нет вовсе у этого действия —
добавить, как у `archiveUser`).
