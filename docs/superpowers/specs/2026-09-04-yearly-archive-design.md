# Годовой архив обзора рынка (сравнение год к году)

Дата: 2026-09-04
Статус: черновик, одобрен пользователем в чате, ждёт написания плана внедрения

## Проблема

Сейчас в системе есть только один переключатель «Период сбора»: открыт/закрыт,
с именем-меткой (например «Обзор рынка — сентябрь 2026»). Эта метка нигде не
используется дашбордом для фильтрации — дашборд («Обзор», «По регионам»,
«Бенчмаркинг» и т.д.) всегда берёт **все** анкеты (`surveys`), которые
когда-либо были заполнены (`SELECT * FROM surveys WHERE state != 'удалена'`,
`src/services/analyticsService.js:255`), без учёта года.

Компания проводит обзор рынка ежегодно и хочет:
1. В следующем году начать заполнение анкет «с чистого листа» — старые цифры
   не должны мешать/путаться с новыми при заполнении.
2. При этом иметь возможность посмотреть и сравнить данные по годам отдельно
   на дашборде («2026» отдельно от «2027»), не теряя ничего.

## Цель / не-цель

**Цель:** разделить анкеты по годам сбора, дать дашборду переключатель года,
и сделать так, чтобы открытие нового периода давало пустую форму заполнения
для каждого подразделения-конкурента.

**Не цель (сознательно не делаем в этой версии):**
- Не архивируем и не трогаем сам список компаний-конкурентов (таблица
  `competitors`) — компании и их ответственные остаются как есть из года в
  год, меняется только статус актуальности каждой записи.
- Не делаем «заморозку» отчёта (Вариант 3 из обсуждения) — цифры годового
  архива продолжают пересчитываться вживую по текущей формуле аналитики,
  а не сохраняются статичным снимком. Если понадобится в будущем — отдельная
  задача.
- Не переносим физически строки в отдельную архивную таблицу (Вариант 2) —
  при текущем объёме данных (сотни/тысячи записей) это не нужно.

## Данные, откуда взято текущее поведение

- `periods` — `src/db/schema.sql:103`: `id, name, state, from_date, to_date,
  updated_by, updated_at`. Только последняя строка (`ORDER BY id DESC LIMIT
  1`) считается «текущей» — используется в `authController`,
  `analyticsService`, `surveyController`, `adminController.setPeriod`.
- `surveys` — `src/db/schema.sql:60`: содержит текстовое поле `period`
  (имя периода на момент **создания** строки), не используется для фильтрации
  нигде, и не обновляется при последующем редактировании той же строки.
- `competitors` — `src/db/schema.sql:39` (список компаний-конкурентов,
  которых опрашивают, каждая привязана к своему подразделению Фаровон через
  `unit`): поле `actual` — `'актуально' | 'не актуально' | 'уточнить'`.
  Не путать с `divisions` (`src/db/schema.sql:24`) — это оргструктура самого
  Фаровон (`unit, dir, head, resp, hrbp`), её эта задача не трогает.
- Заполнение анкеты (`surveyController.js` вокруг строк 380-420 и 490-530):
  поиск «есть ли уже запись» идёт по паре (подразделение, должность,
  компания) **без учёта года** — если запись есть, она **обновляется**
  (`UPDATE`), а не создаётся заново. Значит просто добавить фильтр на
  дашборде недостаточно: без изменения этой логики поиска, заполнение в
  новом году перезапишет прошлогоднюю запись вместо создания новой.

## Дизайн

### 1. Схема данных

- В таблицу `surveys` добавляется колонка `period_id INTEGER` — жёсткая
  ссылка на `periods.id` (а не сравнение по текстовому имени, которое можно
  переименовать). Существующая колонка `period` (текст) остаётся как есть,
  для обратной совместимости и истории отображения — не убираем.
- Миграция: всем существующим строкам `surveys` проставляется
  `period_id = <id самой первой строки periods>` (то есть весь текущий
  массив данных считается «первым годом» архива).
- В `competitors` новых колонок не требуется — поле `actual` уже есть.

### 2. Заполнение анкеты — поиск «уже есть запись» с учётом года

Логика в `surveyController.js`, которая ищет существующую строку по
(unit, pos_our, company) для решения INSERT vs UPDATE (и аналогично в ветке
смежных площадок), дополняется условием `AND period_id = <id текущего
открытого периода>`. Так же меняется место, откуда фронт получает список
уже заполненных строк для показа в форме — тот запрос тоже фильтруется по
текущему `period_id`.

Результат: как только открыт новый период, у него ещё нет ни одной строки
`surveys` с этим `period_id` → форма для любого подразделения пустая →
заполнение создаёт новую строку, а не трогает прошлогоднюю.

### 3. Открытие нового периода (`adminController.setPeriod`, ветка «открыт»)

Помимо существующего создания новой строки в `periods`, действие
дополнительно одним запросом сбрасывает статус актуальности всех
компаний-конкурентов: `UPDATE competitors SET actual = 'уточнить'`.

Ничего не удаляется и не перезаписывается необратимо — старые строки
`surveys` остаются с прежним `period_id`, весь процесс обратим (можно
переоткрыть старый период вручную через админку, если понадобится откатить).

### 4. Дашборд — переключатель года

- `analyticsService` получает необязательный параметр `periodId`; если он
  не передан — используется id последнего (текущего) периода, как
  «умолчание по умолчанию».
- Основной запрос `SELECT * FROM surveys WHERE state != 'удалена'`
  дополняется `AND period_id = ?`. Все вкладки (Обзор, По регионам,
  Бенчмаркинг → «внутренний сбор») автоматически наследуют фильтр, так как
  все они считаются из одного и того же набора строк.
- На дашборде вместо (или рядом с) текущего бейджа периода — выпадающий
  список годов, собранный из `SELECT id, name FROM periods ORDER BY id
  DESC`. Выбор года перезапрашивает дашборд с этим `periodId`.
- Год, отличный от самого нового, открывается **только на просмотр** —
  кнопки редактирования анкет в интерфейсе для него скрываются (аналогично
  тому, как сейчас скрываются при статусе «закрыт»).

### 5. Права доступа

- Открывать новый период / архивировать — действие уже защищено правом
  `period:edit` на сервере (`src/routes/api.js:102`, роль `hrbp` и `admin`
  имеют его по умолчанию — `src/config/capabilities.js:52`). Сейчас кнопка
  «Открыть новый период» на фронте (`renderAdminPeriod`,
  `public/app.js:7512`) рендерится любому, кто просто видит вкладку
  «Период сбора» (право `period:view`), без отдельной проверки права на
  само действие — если в будущем появится роль с `period:view`, но без
  `period:edit`, кнопка будет видна, но нажатие вернёт ошибку доступа с
  сервера. По просьбе пользователя это исправляется: кнопка рендерится
  только при `hasCap('period:edit')` — нет права → кнопки просто нет на
  экране, а не бесполезная кнопка с ошибкой при клике.
- Переключатель года на дашборде виден всем, у кого есть доступ к
  дашборду вообще (`dashboard:view`) — это просмотр, а не действие.

### 6. Граничные случаи

- **Дашборд для года без единой анкеты** (только что открыли новый год) —
  показывает те же самые «пусто» состояния, что сейчас видны при пустых
  данных (например текст «Разрез по регионам пуст»), не ошибку.
- **Смежная группа площадок** (общий `group_key` в `divisions`) — фильтр по
  `period_id` применяется одинаково внутри группового INSERT/UPDATE, чтобы
  копирование анкеты по всем площадкам группы тоже уважало год.
- **Повторное открытие периода без закрытия предыдущего** — кнопки в
  админке уже устроены так, что видна только одна из двух («Открыть» либо
  «Закрыть») в зависимости от текущего состояния — это поведение не
  меняется.

## Тестирование

- Юнит-тест: заполнение анкеты для подразделения, у которого уже есть
  запись за **другой, закрытый** `period_id`, создаёт новую строку (не
  апдейтит старую).
- Юнит-тест: `analyticsService` с явным `periodId` возвращает только строки
  этого периода; без параметра — данные текущего (последнего) периода.
- Юнит-тест: `setPeriod` с `state: 'открыт'` сбрасывает `actual` всех строк
  `competitors` на `'уточнить'`.
- Ручная проверка в браузере: заполнить анкету в периоде A → открыть период
  B → форма для того же подразделения пустая → заполнить заново с другими
  цифрами → на дашборде переключить год на A — видно старые цифры,
  переключить на B — видно новые.
