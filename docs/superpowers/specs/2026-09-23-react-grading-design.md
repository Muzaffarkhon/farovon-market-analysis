# Дизайн: этап 5 — оценка должностей и риски ключевого персонала (новый клиент)

Дата: 2026-09-23. Ветка `redesign/react`. Продолжение
`2026-09-23-react-coordination-design.md`. Источник требований —
`docs/ТЗ_переписывание_интерфейса_2026-09-22.md`, разделы 6 и 7.

## 1. Зачем

Два модуля объединены в один этап ТЗ (раздел 14), но это разные экраны с
разными правами: грейдирование оценивает **должность** (требование к
функции, общее для всех подразделений блока), риски незаменимости —
**конкретного человека**. Их роднит форма: анкета из фиксированных
факторов 1–5, посчитанная в `services/gradingService.js`, уже полностью
математически готовая и покрытая тестами (`test/gradingService.test.js`).
Серверная часть (`gradingController.js`, 20 маршрутов) не меняется вовсе —
этот этап целиком клиентский, что отличает его от этапов 3–4.

## 2. Область видимости

Существующие права, без изменений: `grading:view`/`grading:edit` — оценка
должностей; `keyrisk:view`/`keyrisk:edit` — риски. Видимость подразделений
— `allowedUnits`/`canUseUnit` уже в `gradingController.js` (admin/cb — весь
холдинг, остальные — `users.units`), сервер сам возвращает 403 при попытке
обратиться к чужому подразделению — клиент не дублирует эту проверку.

**Сознательно вне этого этапа** (административная настройка, не заполнение
анкеты — по аналогии с тем, как импорт/сопоставление бенчмарка остались
администрированию на этапе 3):
- `grading:factors` — правка формулировок вопросов
- `grading:blocks` — состав индустриальных блоков, перенос должности между
  блоками, сброс утверждённой оценки
- `grading:committee` — состав комиссии по блоку, принудительное подведение
  итога

Эти три права переезжают в раздел «Администрирование» (этап 6) вместе с
остальной настройкой справочников. Заполнение анкеты (`grading:edit`,
включая слепую заявку члена комиссии) и просмотр (`grading:view`) —
здесь, в основном разделе.

Удаление записи риска (`requireRoles('admin')`) остаётся в объёме этого
этапа — это одна кнопка в списке, а не отдельная админ-подсистема.

## 3. Сервер

Не меняется. Ниже — только карта того, что уже есть и как этим пользуется
клиент (без новых маршрутов, без новых полей).

| Маршрут | Право | Для чего |
|---|---|---|
| `GET /grading/factors?dir=` | любое из четырёх | Тексты анкеты; `dir=block:<key>` — переопределение под блок |
| `GET /grading/blocks` | view/edit | Карточки блоков: прогресс, число оценённых |
| `GET /grading/positions?block=` | view/edit | Должности блока + своя слепая заявка, если есть комиссия |
| `POST /grading/evaluate` | edit | Сохранение — сервер сам решает: прямая запись или слепая заявка (см. 4.3) |
| `GET /grading/stats` | view/edit | Распределение по грейдам — для сводки |
| `GET /key-personnel/list?unit=&status=` | view/edit | Список оценённых сотрудников |
| `GET /key-personnel/unit-employees?unit=` | edit | ФИО для выпадающего списка анкеты (не свободный текст) |
| `POST /key-personnel/evaluate` | edit | Сохранение анкеты риска |
| `GET /key-personnel/heatmap` | view/edit | Направление × уровень риска → число сотрудников |
| `POST /key-personnel/delete` | роль admin | Полное удаление записи риска |

## 4. Клиент — «Оценка должностей»

### 4.1 Маршрут

`/grading/:block?` — «Оценка должностей». Блок в пути, как вкладка
дашборда: `/grading/production`, `/grading/office` и т.д. Без блока —
экран с карточками блоков (раздел 4.2), выбор блока переводит на его
путь.

### 4.2 Карточки блоков

Список из `GET /grading/blocks`: название, полоса прогресса
(`evaluated_count`/`position_count`), балл — сюда чисто не ложится
(блок — не одно число), поэтому справа число «N из M оценено». Клик —
переход на `/grading/:key`.

### 4.3 Список должностей блока + анкета

- **Таблица** должностей блока (`GET /grading/positions`): должность,
  число подразделений (с подсказкой — список из `row.units`), штат
  суммарно, статус (`не начата` / `идёт оценка N из M` при комиссии /
  `оценена`, балл и грейд, если есть).
- Клик по должности открывает **анкету** сбоку/шторкой: семь факторов
  (`CRITERIA` из `/grading/factors`), у каждого — пять карточек-вариантов с
  текстом и эталонной должностью (`examples[i]`) под выбранным; примечание;
  кнопка «Отправить оценку».
- Если у блока есть комиссия (`isCommitteeMember`/`committeeSize` в ответе
  `getPositions`) и должность уже утверждена — форма недоступна на запись,
  показывается только итог (сервер и так откажет 409, но не показывать
  недоступную форму — не заставлять узнавать об этом через ошибку).
- Ответ `evaluate` различается: `pending: true` (сдал, ждём остальных —
  тост с «сдали N из M»), `finalized: true` (комиссия закрыла — итог сразу
  на экране), обычный `{weightedScore, gradeLevel}` без комиссии.
- **Сводка** (`GET /grading/stats`) — отдельной строкой/кнопкой у карточек
  блоков: распределение должностей по пяти группам, не отдельный экран.

### 4.4 Общие визуальные примитивы

Новый `design/ScaleInput` — ряд из пяти кнопок-карточек 1–5 (мокап
`06-grading.html`): активная подсвечена, под ней — `examples[value-1]`,
если есть. Переиспользуется анкетой должностей; анкета риска использует
обычные `Select`, потому что там варианты — целые фразы-ситуации без
эталонной должности (раздел 6 ТЗ: «для анкеты рисков эталонов нет»).

## 5. Клиент — «Риски ключевого персонала»

### 5.1 Маршрут

`/key-risks` — «Риски». Одна страница, без вкладок: тепловая карта +
список, как в мокапе `07-risks.html`.

### 5.2 Экран

- **KPI-плитки**: оценено сотрудников (из скольких ключевых — общее число
  берётся из суммы по тепловой карте), критический риск, зона внимания,
  штатных. `KpiTile` — тот же компонент, что у дашборда.
- **Тепловая карта** (`GET /key-personnel/heatmap`): строки —
  направления, три цветные ячейки (штатный/внимание/критический) с
  числом. Переиспользовать `RankBar`/`ForkBar` не выйдет (это не вилка и
  не рейтинг одного значения) — простая сетка `<table>`, ячейка красится
  по уровню (`--ok`/`--warn`/`--danger`).
- **Список «Требуют внимания»** — `GET /key-personnel/list?status=attention`
  и `?status=critical` вместе, отсортировано по баллу убыв. (сервер уже
  так сортирует). Строка: сотрудник, должность, подразделение, балл,
  статус, план действий; кнопка «Оценить заново» открывает анкету; кнопка
  «Удалить» — только `role === 'admin'`.
- **Кнопка «Оценить сотрудника»** — открывает шторку: подразделение (свои,
  если не admin/cb) → сотрудник (`GET /key-personnel/unit-employees`,
  выпадающий список, не текст) → четыре вопроса `Select`'ами (без весов,
  простая сумма) → сохранение.

## 6. Тесты

Серверные тесты не пишутся — сервер не меняется, `gradingService.test.js`
уже покрывает математику. Клиент — `vitest`:
- `ScaleInput` — выбор значения, показ эталона под активным вариантом
- Блоки: карточки рендерятся, клик ведёт на `/grading/:key`
- Список должностей: статусы (не начата/идёт/оценена) по данным ответа
- Отправка анкеты: три ветки ответа (`pending`/`finalized`/обычный) дают
  разный текст тоста
- Риски: тепловая карта красит ячейки по уровню; список «Требуют
  внимания» объединяет `attention`+`critical`; выбор подразделения сужает
  список сотрудников до `unit-employees`; кнопка «Удалить» не видна не-admin

## 7. Чего здесь нет

Правки формулировок анкеты, состава блоков, состава и принудительного
подведения итогов комиссии — раздел 2 (`grading:factors`/`grading:blocks`/
`grading:committee`), переезжают в «Администрирование» (этап 6). Импорта
`staff_directory` из 1С — это тоже этап 6 (справочники). Пересчёта
методики (7 факторов, веса, пороги) — не входит в объём переписывания
интерфейса.
