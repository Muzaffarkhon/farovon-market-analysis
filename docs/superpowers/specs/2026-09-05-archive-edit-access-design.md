# Точечный доступ на редактирование архивного года

Дата: 2026-09-05
Статус: черновик, одобрен пользователем в чате, ждёт написания плана внедрения
Опирается на: [2026-09-04-yearly-archive-design.md](2026-09-04-yearly-archive-design.md) (годовой архив — уже реализован, см. `docs/superpowers/plans/2026-09-04-yearly-archive.md`)

## Проблема

После внедрения годового архива редактирование анкет возможно только в
текущем (последнем) периоде сбора — прошлые годы доступны исключительно на
просмотр через переключатель года на дашборде. Это осознанное решение
прошлой задачи, но иногда нужно точечно исправить ошибку в уже закрытом
году (например, HR BP нашёл опечатку в окладе, который сам же в прошлом
году и вносил). Сейчас для этого нет способа, кроме прямого вмешательства
в базу.

## Цель / не-цель

**Цель:** дать админу возможность точечно и временно разрешить конкретному
сотруднику редактировать конкретный архивный год, с автоматическим
истечением доступа.

**Не цель:**
- Не даём доступ на редактирование ролью целиком (только конкретному
  человеку — по требованию пользователя, чтобы не открывать разом всем
  HR BP доступ, когда нужен один).
- Не даём точную настройку срока доступа при выдаче — фиксировано 24 часа,
  без выбора длительности (по требованию пользователя — минимум кликов для
  админа).
- Сам админ (роль `admin`) в этом ограничении не участвует — он может
  редактировать любой архивный год всегда, без выдачи себе гранта.
- Не меняем список подразделений, доступных человеку — грант расширяет
  «какой год», а не «какие подразделения»: обычные ограничения по
  `users.units`/`hrbp` продолжают действовать как и для текущего периода.

## Данные, откуда взято текущее поведение

- `surveys.period_id` — жёсткая привязка анкеты к году сбора (см. прошлую
  спеку). Форма заполнения (`openUnit()`, `public/app.js:1434`) берёт
  рабочий набор анкет из `S.data.surveys` — а он приходит из
  `authController.getUserPayload` → `userSurveysPromise`
  (`src/controllers/authController.js`), уже отфильтрованного по ТЕКУЩЕМУ
  `period_id`. Другого способа увидеть/отредактировать анкету другого года
  через эту форму сейчас нет.
- Сохранение анкеты — `POST /api/survey/save-details`
  (`src/routes/api.js:65`) → `surveyController.saveSurveyDetails`. Сейчас
  всегда резолвит период как «последний по `id`» (`SELECT id, state, name
  FROM periods ORDER BY id DESC LIMIT 1`) и не принимает от фронта, за
  какой период идёт сохранение — целевой период жёстко «текущий».
- Право `period:edit` (`src/config/capabilities.js:28`) сейчас управляет
  открытием/закрытием периода (`admin`, `hrbp` — по умолчанию, см. строку
  52 того же файла) и с прошлой задачи — видимостью кнопки в
  `renderAdminPeriod` (`public/app.js`).

## Дизайн

### 1. Новая таблица `period_edit_grants`

```sql
CREATE TABLE IF NOT EXISTS period_edit_grants (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_login TEXT NOT NULL,
  period_id INTEGER NOT NULL REFERENCES periods(id),
  granted_by TEXT NOT NULL,
  granted_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  expires_at DATETIME NOT NULL,
  UNIQUE(user_login, period_id)
);
```

`UNIQUE(user_login, period_id)` — повторная выдача тому же человеку на тот
же год не создаёт вторую строку, а **заменяет** существующую (продлевает
24 часа заново от момента повторной выдачи). Реализуется через `INSERT ...
ON CONFLICT(user_login, period_id) DO UPDATE SET granted_by = excluded.
granted_by, granted_at = CURRENT_TIMESTAMP, expires_at = excluded.
expires_at` (libSQL/SQLite поддерживает `ON CONFLICT DO UPDATE`).

Просроченные строки не обязательно удалять — они не мешают (запрос всегда
фильтрует `WHERE expires_at > CURRENT_TIMESTAMP`) и заодно остаются
историей «кому когда что выдавали» для аудита. Ручного/автоматического
удаления не делаем — YAGNI.

### 2. Проверка доступа при сохранении

`surveyController.saveSurveyDetails` (и её ветка смежных площадок)
принимает от фронта необязательный `periodId` в теле запроса:

- Не передан → как сейчас, целевой период = последний по `id` (текущий).
- Передан и равен id последнего периода → тоже как сейчас, без
  дополнительной проверки (текущий год редактировать можно всем, кому
  можно и так).
- Передан и НЕ равен id последнего периода (значит это архивный год) →
  дополнительная проверка:
  - `req.user.role === 'admin'` → разрешено всегда, без гранта.
  - Иначе → `SELECT 1 FROM period_edit_grants WHERE user_login = ? AND
    period_id = ? AND expires_at > CURRENT_TIMESTAMP` — если строки нет,
    `403 { error: 'Нет доступа к редактированию этого периода' }`.

При прохождении проверки весь остальной код функции (поиск существующей
строки, INSERT/UPDATE, привязка `period_id` к новым строкам) использует
этот целевой `periodId` вместо всегда-последнего — то есть та же логика,
что уже фильтрует по `period.id` сегодня, просто `period.id` берётся не
всегда из «последнего», а из проверенного целевого периода.

### 3. Новый эндпоинт: анкеты подразделения за конкретный (архивный) год

Форме нужно чем-то заполниться, когда переключаешься на архивный год —
сейчас `S.data.surveys` содержит только текущий год. Новый эндпоинт:

`POST /api/survey/for-period` → `{ unit, periodId }` → тот же формат строк,
что и `userSurveysPromise` сейчас, но `WHERE unit = ? AND period_id = ? AND
state != 'удалена'`, с той же проверкой доступа, что в разделе 2 (admin —
без ограничений; иначе — активный грант на этот `periodId`, либо это
текущий период). Не кэшируется через `refCache` — как и обычные
пользовательские данные (см. комментарий в `src/services/refCache.js`),
это данные, которые не должны залипать даже на короткий TTL при
одновременной работе двух людей с одним архивным годом.

### 4. Что видит сотрудник на сессии (`getUserPayload`)

В ответ `getUserPayload` добавляется `myPeriodGrants:
[{periodId, periodName, expiresAt}]` — только АКТИВНЫЕ (не истёкшие) гранты
текущего залогиненного пользователя. Фронт использует это только чтобы
решить, показывать ли переключатель на форме (раздел 6) — без грантов
массив пустой, ничего нового не видно, поведение не отличается от того,
что есть сейчас.

### 5. Админский экран — выдача и отзыв

В `renderAdminPeriod` (`public/app.js`, та же вкладка «Период сбора»), под
существующей карточкой текущего периода — новый блок «Доступ к
редактированию архива»:

- Выбор сотрудника (список активных пользователей, как в других местах
  админки) + выбор периода (список периодов ИСКЛЮЧАЯ последний/текущий —
  ему грант не нужен) + кнопка «Выдать на 24 часа».
- Backend: `POST /api/admin/period-grants` (`{ userLogin, periodId }`),
  защищено тем же `period:edit`, что и открытие/закрытие периода. Делает
  `INSERT ... ON CONFLICT DO UPDATE` из раздела 1, пишет `audit_log`
  (`'выдан доступ к архивному периоду'`, кто/кому/какой период/до какого
  времени).
- Список активных грантов ниже: сотрудник, год, «истекает через Xч Yм» —
  считается на фронте от `expiresAt`, не обновляется сам собой (просто
  пересчитывается при следующей загрузке экрана — не нужен таймер в
  реальном времени, YAGNI).
- Кнопка «Отозвать» на каждой строке → `POST /api/admin/period-grants/
  revoke` (`{ userLogin, periodId }`) → `DELETE FROM period_edit_grants
  WHERE user_login = ? AND period_id = ?`, тоже в `audit_log`.
- `GET`-часть списка — новый эндпоинт `GET /api/admin/period-grants` →
  `SELECT g.user_login, u.fio, g.period_id, p.name AS period_name,
  g.granted_by, g.granted_at, g.expires_at FROM period_edit_grants g JOIN
  periods p ON p.id = g.period_id LEFT JOIN users u ON u.login =
  g.user_login WHERE g.expires_at > CURRENT_TIMESTAMP ORDER BY
  g.expires_at DESC` — один запрос с join, без отдельных обращений на
  фронте.

### 6. Переключатель на форме заполнения (`openUnit`, `public/app.js:1434`)

Если `S.data.myPeriodGrants` непусто, над формой (там же, где сейчас
просто открывается подразделение) рендерится маленький переключатель:
«Вы редактируете: [2027 (текущий)] · [2026 (архив, до 15:40)]» — по одной
кнопке на каждый активный грант плюс всегда одна на текущий год.

- Клик на архивный год → `call('apiSurveysForPeriod', unit, periodId)`
  (новый эндпоинт из раздела 3) → подставляет результат в `S.surveys`
  вместо текущего среза `S.data.surveys`, запоминает `S.editingPeriodId =
  periodId` для этой сессии редактирования подразделения.
- Сохранение (`apiSaveSurvey`) добавляет `periodId: S.editingPeriodId ||
  null` в тело запроса — `null`/отсутствие означает «текущий», как сейчас.
- Переключение обратно на текущий год восстанавливает `S.surveys` из
  `S.data.surveys` (как было до этой задачи) и сбрасывает
  `S.editingPeriodId`.
- Если у пользователя истёк грант ПОКА он редактирует (маловероятно за
  типичную сессию, но возможно) — сервер просто вернёт 403 при сохранении
  с понятным текстом ошибки; отдельного «отсчёта в реальном времени» на
  самой форме не делаем — YAGNI, ошибка сервера — достаточная страховка.

### 7. Права доступа

- Выдача/отзыв гранта — `period:edit` (тот же, что открытие/закрытие
  периода) — те же роли, что сейчас управляют периодом, управляют и этим.
- Использование гранта (сохранение в архивный год) — сам факт наличия
  активной строки в `period_edit_grants` для этого пользователя+периода,
  роль не имеет значения (кроме `admin`, который всегда может без гранта).
- Обычные ограничения по подразделениям (`users.units`, `hrbp`) продолжают
  действовать как обычно — грант не открывает доступ к чужим
  подразделениям, только к своему подразделению за другой год.

## Тестирование

- Юнит-тест (чистая функция): `isGrantActive(expiresAt, now)` — простая
  функция сравнения дат, выносится ради тестируемости без обращения к БД.
- Скрипт-проверка в `scratch/` (по паттерну прошлой задачи, живая БД,
  теговые тестовые данные, самоочистка): выдать грант тестовому
  пользователю на тестовый архивный период → сохранение с этим `periodId`
  проходит → сохранение с другим (не выданным) архивным `periodId`
  получает 403 → истёкший (искусственно вставленный с `expires_at` в
  прошлом) грант тоже даёт 403 → admin без гранта проходит на любой
  `periodId`.
- Ручная проверка в браузере (сценарий из чата): выдать доступ реальному
  тестовому аккаунту на архивный год → зайти под ним → увидеть
  переключатель → отредактировать → убедиться, что текущий год не
  тронут → отозвать доступ → переключатель пропал, сохранить в архив
  больше нельзя.
