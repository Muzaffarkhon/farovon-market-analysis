# Дизайн: этап 3 — дашборды (новый клиент)

Дата: 2026-09-23. Ветка `redesign/react`. Продолжение
`2026-09-22-react-stage0-1-design.md` и `2026-09-23-react-registry-design.md`.
Источник требований — `docs/ТЗ_переписывание_интерфейса_2026-09-22.md`, раздел 5.

## 1. Зачем

Дашборды — то, ради чего вообще собираются данные: медиана рынка, вилки по
должностям, разрезы по регионам и льготам, прогресс сбора, сравнение с внешним
бенчмарком. Сегодня всё это — вкладки внутри одного тяжёлого экрана старого
клиента, который тянет `/api/dashboard/extended` (весь расчёт разом, включая то,
что уже переехало в отдельный реестр) и рисует шесть вкладок из одного объекта
на 300+ строк кода. Разрезов по надёжности, источнику и графику работы нет вовсе
— компании с 40-часовой и 54-часовой неделей, с высокой и низкой достоверностью
источника смешиваются в одной медиане.

В новом клиенте — свой раздел `/dashboard` с шестью вкладками по мокапам
(`docs/presentation/mockups/04-dashboard.html`, `05-benchmark.html`), с
новыми разрезами и с бенчмарком, показанным на равных с остальной аналитикой,
а не отдельным пунктом меню.

## 2. Область видимости

Право — `dashboard:view`, тот же предикат видимости, что у реестра
(`services/scopeService.js`, `unitScopeFilter`): admin и C&B — весь рынок, HR BP
— свои подразделения, руководители — закреплённые. Вкладка «Бенчмаркинг»
дополнительно требует `benchmarks:view` — без него вкладка не показывается в
навигации вкладок, а не запрещается отдельной страницей.

## 3. Сервер

### 3.1 Новый маршрут вместо `/dashboard/extended`

**Уточнение при реализации:** `getHRBPDashboard` — не то же самое, что
`getCBDashboard`. Это не альтернативная ролевая обёртка над той же
аналитикой, а отдельный экран координации: строка на подразделение
(«не начато» / «в процессе» / «заполнено», кто последний вносил данные) —
своя выборка из `divisions`/`position_company_selections`/`surveys`, без
`getExtendedAnalytics`. По разделу 14 ТЗ это «Координация для HR BP» —
**этап 4**, не этап 3, и в этой спеке не трогается.

`getCBDashboard` в `dashboardController.js` — тонкая обёртка над
`getExtendedAnalytics(filters, { unitFilter })` с ролевым предикатом из
`scopeService`. Новый клиент ходит в `POST /api/dashboard` — тот же вызов,
явно названный маршрутом, а не завязанный на историческое имя «CB». Старый
`/dashboard/extended` остаётся нетронутым для старого клиента до его
отключения (этап 9); `getHRBPDashboard`/`/dashboard/hrbp` не трогаются вовсе.

Запрос — те же фильтры, что уже принимает `getExtendedAnalytics`:
`{ period?, dir?, hrbp?, region? }`. Ответ — форма `getExtendedAnalytics` из
раздела 3.2, без изменений в существующих полях.

### 3.2 Разрезы, которых не хватает (`analyticsService.js`)

Каждый — отдельная функция с собственным тестом, без переписывания
`getExtendedAnalytics`: они читают те же строки, которые функция уже разобрала
в `rawRows` внутри цикла по `surveys`, и добавляют свою агрегацию рядом с уже
существующими (`regionSamples`, `benefitStats` и т.д.), тем же способом.

1. **По надёжности** (`trustStats`) — как `regionStats`, но группировка по
   `s.trust` (`высокая` / `средняя` / `низкая` / пусто → `не указана`). Вилка
   `calculateSalaryForkStats` на тех же приведённых к месяцу суммах.
2. **По источнику** (`sourceStats`) — то же самое, группировка по `s.source`
   без нормализации значений (источники — свободный текст анкеты, показываем
   как есть, топ-10 по числу наблюдений, остальное — «другое»).
3. **По графику работы** (`scheduleStats`) — то же самое, группировка по
   `s.schedule` из справочника (`authController.js` возвращает список из 8
   значений). Не приводить графики друг к другу — просто не смешивать в одной
   медиане, отдельная строка на каждый график.
4. **Прочие выплаты в совокупном доходе** — сегодня `totalMedian` по должности
   считает только оклад + премия (см. `positionsList` в `getExtendedAnalytics`
   и `totalMonthly` в `registryService.js`, который решает эту же задачу для
   реестра). Перенести туда же правило «нет» → известный ноль, принятое сегодня
   для реестра (`bonusMonthly = bonHas === 'нет' ? 0 : varPay.monthly`), и
   прибавить `extra`, когда он похож на число (`parseBonusSize` уже умеет это
   делать для `bon_size` — переиспользовать).
5. **Конвертация валют** — строки с `cur !== 'сомони'` сегодня не отделены и
   попадают в общую медиану как есть. `services/fxService.js` уже даёт курсы для
   бенчмарка; та же функция даёт курс на дату наблюдения (`s.created_at`) для
   вилок. Строки без курса на дату (валюта не в справочнике) — исключаются из
   общей медианы и помечаются `fxMissing` в реестре наблюдений, не гадаем.
6. **Вилки по грейдам** (`gradeStats`) — то же самое, группировка по
   `s.grade` (пусто исключается — грейд заполняется только импортом).

Общий вид элемента разреза — как у `regionStats`:
`{ key, count, min, p25, median, p75, max, avg }`. Ответ `getExtendedAnalytics`
получает четыре новых массива: `trustStats`, `sourceStats`, `scheduleStats`,
`gradeStats`; `summary.salaryMedian` и `positions[].totalMedian` меняют расчёт
по пунктам 4–5 без изменения формы ответа.

### 3.3 Бенчмаркинг — что показываем на дашборде

Только чтение: `benchmarkService.compare({ positionId, positionName, user })` и
`getBenchmarkSummaryWidgets({ user })`, уже отданные маршрутами
`GET /benchmarks/compare` и `GET /benchmarks/summary-widgets` за
`benchmarks:view`. Настройка источников, импорт, сопоставление должностей —
инструменты администратора C&B, это `benchmarks:import`/`benchmarks:map`, и
они не часть дашборда — переезжают в раздел «Администрирование» (этап 6).

## 4. Клиент

### 4.1 Маршрут и навигация

`/dashboard/:tab?` — «Дашборды», вкладки: `overview`, `salaries`, `regions`,
`benefits`, `benchmark`, `progress`. Вкладка в адресе (не в состоянии компонента)
— чтобы ссылку на конкретный разрез можно было переслать и чтобы «назад»
возвращала предыдущую вкладку, как уже сделано для фильтров реестра. Фильтры
дашборда (направление, HR BP, регион, период) — тоже в query-параметрах, тем же
хуком, что и `useRegistry` (общий `usePeriodId` уже есть в `features/shell`).

Пункт меню виден при `dashboard:view`; вкладка «Бенчмаркинг» — дополнительно при
`benchmarks:view` (см. `NavItems.ts`, где уже есть подобная условная логика для
`survey:fill`).

### 4.2 Общие элементы экрана

- **Плитка KPI** (`design/`, новый компонент `KpiTile`) — число крупно, подпись
  мелко под ним, единица измерения рядом с числом. Не больше четырёх в ряд
  (раздел 10 ТЗ), на телефоне — в столбец.
- **Строка вилки** (`design/`, новый компонент `ForkBar`) — горизонтальная
  шкала по образцу мокапа: тонкая линия min–max, закрашенный блок P25–P75,
  риска медианы, число медианы справа. Один компонент переиспользуется в
  «Зарплатных вилках», «По регионам», «По надёжности/источнику/графику/грейду».
- **Полоса рейтинга** (`design/`, новый компонент `RankBar`) — подпись, процент
  справа, закрашенная полоса — для льгот, топ-компаний, типов премии.
- Общие фильтры (направление, HR BP каскадом от направления, регион, период) —
  одна панель наверху раздела, одинаковая на всех вкладках (как у мокапа), а не
  повторяется в каждой.

### 4.3 Вкладка «Обзор»

KPI-плитки: медиана рынка (P50), «Фаровон к рынку» (среднее `gapPct` по
должностям с известным гэпом), размах вилки (P25–P75 в процентах от медианы),
доля компаний с премией. Ниже — топ-6 должностей по числу наблюдений строками
`ForkBar`, и карточка «Рейтинг льгот» (топ-5, `RankBar`) сбоку — один в один как
мокап `04-dashboard.html`.

### 4.4 Вкладка «Зарплатные вилки»

Список всех должностей (`positions[]`) строками `ForkBar` с поиском по названию
(тот же `searchPos`, что уже принимает сервер) и сортировкой по числу
наблюдений / медиане / гэпу. По клику на должность — шторка с компаниями,
давшими данные (то, что уже copится в `positions[].companies`), включая
переменную часть и совокупный доход — переиспользуется вёрстка ячеек из
`RecordSheet.tsx` реестра, а не пишется заново.

### 4.5 Вкладка «По регионам»

Таблица регионов (`regionStats`) с вилками, отсортированная по медиане — как
раздел 4 мокапа, но строками таблицы вместо карточек: регион, число
наблюдений, min/P25/медиана/P75/max.

### 4.6 Вкладка «Льготы и бонусы»

Две колонки: рейтинг льгот целиком (`topBenefits`, `RankBar` на каждую), и
переменная часть — доля компаний с премией / без / неизвестно (`bonuses.hasBonus`
и т.д.), топ видов премии и типичная периодичность.

### 4.7 Вкладка «Бенчмаркинг»

Выбор должности (тот же справочник, что в анкете) → таблица источников
(`compare`) с весом каждого источника и итоговой рекомендованной вилкой — по
образцу `05-benchmark.html`: серая шапка, полоса веса, крупные цифры. Сверху —
виджеты `getBenchmarkSummaryWidgets` (сколько источников подключено, сколько
должностей сопоставлено). Кнопки импорта и сопоставления не показываются без
`benchmarks:import`/`benchmarks:map` — их в этом разделе нет вообще (см. 3.3).

### 4.8 Вкладка «Прогресс»

Две таблицы рядом (или друг под другом на телефоне): по HR BP и по направлениям
(`hrbpProgress`, `dirProgress`) — подразделение, доля закрытых должностей,
полоса прогресса. Только чтение: переназначение ответственных и напоминания —
это «Координация для HR BP», этап 4.

### 4.9 Загрузка и пустые состояния

TanStack Query, ключ — вкладка + нормализованные фильтры,
`placeholderData: keepPreviousData` при смене фильтров (как в реестре).
Скелетоны на плитках и строках вилок при первой загрузке. Пустой рынок (ни
одной заполненной записи) — одно сообщение на весь раздел, без вкладок с
пустыми графиками.

## 5. Тесты

- `analyticsService` — `node --test`: каждый новый разрез отдельно (вилка
  считается верно, пустые группы не попадают, приведение ЧТС/сдельных работает
  как в существующих разрезах); совокупный доход с «нет премии» → известный
  ноль; конвертация валют — строка без курса на дату исключается из общей
  медианы и помечена `fxMissing`, но не выпадает из `rows`.
- Маршрут `/api/dashboard` — доступ без `dashboard:view` отдаёт 403; форма
  ответа не ломает существующие `/dashboard/extended` и `/dashboard/hrbp`
  (регрессия на общих фикстурах, если такие уже есть в `test/`, иначе — новые).
- Клиент — `vitest`: КPI-плитки показывают число из ответа; `ForkBar` рисует
  корректные проценты по min/p25/median/p75/max (в т.ч. вырожденный случай
  min===max); вкладка и фильтры уходят в адрес; вкладка «Бенчмаркинг» не видна
  без `benchmarks:view`; пустой рынок — одно сообщение, не шесть пустых вкладок.

## 6. Чего здесь нет

Координации для HR BP — переназначения, напоминаний, персональных списков дел
(этап 4). Оценки должностей и рисков ключевого персонала — это отдельные
разделы навигации, не вкладки дашборда (этап 5). Импорта и сопоставления
бенчмарка, администрирования источников (этап 6, вместе с остальным
администрированием). Правки формулы гэпа или методологии перцентилей — она уже
верна и не входит в объём переписывания интерфейса.
