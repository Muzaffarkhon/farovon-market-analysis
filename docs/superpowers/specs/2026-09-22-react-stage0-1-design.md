# Дизайн: новый клиент на React — этапы 0 и 1

Статус: согласован заказчиком 22.09.2026. Исходное ТЗ — `docs/ТЗ_переписывание_интерфейса_2026_09_22.md` (в ветке `redesign/survey-cleanup`); этот документ фиксирует **технические решения** для этапов 0 (каркас) и 1 (сбор данных), которые ТЗ оставляет на исполнителя.

Следующий модуль после этапа 1 — «Пересмотр ЗП» (`2026-09-22-comp-review-design.md`), он строится на этом каркасе.

---

## 1. Сосуществование со старым клиентом

- Новое приложение живёт в папке **`web/`** репозитория. Исходники — там; сборка кладётся в **`client/next/`** (в `.gitignore`, собирается на деплое).
- Express отдаёт сборку по адресу **`/new`** (и `/new/*` → `index.html` для клиентской маршрутизации). Старый клиент остаётся на `/` без изменений.
- Сессия общая: тот же cookie/JWT, тот же `/api/auth/resume`. Отдельного входа нет.
- Деплой: `vercel-build` дополняется шагом `npm --prefix web ci && npm --prefix web run build`. `includeFiles: client/**` в `vercel.json` уже покрывает `client/next/`.
- Локально: `npm run dev` поднимает сервер как сейчас; `npm --prefix web run dev` — Vite с прокси `/api` на порт сервера. Для проверки «как на проде» — `npm run build:web`, после чего `/new` отдаёт собранное.
- Отвергнуто: отдельный репозиторий/домен (два деплоя, две сессии), постепенная замена экранов внутри `app.js` (не решает проблему размера).

## 2. Стек

| Что | Выбор | Почему |
|---|---|---|
| UI | React 19 | требование ТЗ, у заказчика есть опыт |
| Язык | TypeScript, strict | типы контракта API ловят расхождения до запуска |
| Сборка | Vite | быстрая, без конфигурации, одна папка вывода |
| Маршруты | react-router (data-less, простые `<Route>`) | достаточно для экранов; один маршрут = один экран |
| Состояние сервера | TanStack Query | загрузка/ошибки/инвалидация в одном месте |
| Локальное состояние форм | `useState`/`useReducer` внутри формы | по ТЗ |
| Стили | CSS Modules + токены в `:root` | стили рядом с компонентом; без Tailwind, без веб-шрифтов |
| Тема | атрибут `data-theme` на `<html>`, ставится инлайн-скриптом в `<head>` до первой отрисовки из `localStorage` | нет вспышки |
| Иконки | свой набор SVG-компонентов (перенос из `client/icons`) | без внешних зависимостей |
| Тесты | Vitest + Testing Library для компонентов и хуков; серверные тесты — как сейчас `node --test` | |

Правила из ТЗ, закреплённые линтером/структурой: файл > 400 строк — разбить; разметка только JSX (никакой конкатенации строк); бизнес-правило в одном модуле (`web/src/domain/`), экраны его вызывают.

## 3. Структура `web/src`

```
app/            точка входа, провайдеры (Query, Router, Theme, Session), маршруты
api/            client.ts (fetch-обёртка, обработка 401/403/ошибок), contract.ts (типы ответов), по файлу на область: auth.ts, survey.ts, admin.ts
domain/         чистая логика без React: progress.ts (расчёт прогресса), validation.ts (единый контракт валидации анкеты), currency.ts
design/         tokens.css, theme.ts, компоненты: Button, Input, Select, Chip, Badge, Sheet (шторка), Table, Card, Toast, Skeleton
features/
  auth/         Вход, смена пароля, восстановление сессии
  shell/        Верхняя панель, боковая/нижняя навигация, выбор периода, профиль
  access/       Матрица ролей, персональные права со сроком
  survey/       Список подразделений, экран подразделения, лист заполнения, шторка компаний
lib/            утилиты: формат чисел, даты, esc не нужен (JSX)
```

Компонент — 100–300 строк, рядом `Component.module.css` и `Component.test.tsx` при наличии логики.

## 4. Слой API

- Одна обёртка `request(path, body)` над `fetch` с `credentials: 'include'`. Ответы сервера имеют форму `{ ok, ...data }` либо `{ ok: false, error }`; обёртка бросает типизированную ошибку `ApiError` с текстом сервера.
- `401` → сброс сессии и переход на вход; `403` → тост «нет доступа», экран остаётся.
- Типы контракта в `api/contract.ts` снимаются вручную с контроллеров (`src/controllers/*`) **до** написания экранов. Для этапов 0–1 нужны: `auth/login`, `auth/resume`, `auth/logout`, `auth/change-password`, `survey/for-period`, `survey/position-selections`, `survey/position-selection/save`, `survey/save-details`, `survey/dictionary/add`, `admin/role-capabilities` (GET/POST), `admin/user-capabilities` (GET/POST), `admin/divisions` (GET, для списка своих подразделений).
- Ключи кеша Query: `['session']`, `['divisions']`, `['survey', unit, periodId]`, `['selections', unit, periodId]`, `['capabilities', ...]`. После сохранения — инвалидация ключей подразделения (и всех подразделений смежной группы).

## 5. Этап 0 — каркас

**Вход.** Логин/пароль, ошибка текстом под формой, блокировка после 8 попыток показывается сообщением сервера. Требование смены временного пароля — экран сразу после входа. Восстановление сессии — при старте, со скелетоном вместо вспышки формы входа.

**Оболочка.** Верхняя панель: слева навигация (на телефоне — нижняя панель из 4–5 пунктов) и заголовок экрана, справа действия экрана, редкое — под «ещё». Навигация строится из прав и роли пользователя (`capabilities` в ответе `auth/resume`). Выбор периода — в оболочке, хранится в URL-параметре, чтобы ссылка открывала тот же период.

**Дизайн-система.** Токены: цвета (фон, поверхность, текст, приглушённый, акцент, успех/внимание/ошибка), радиусы, отступы 4/8/12/16/24, тени. Компоненты из раздела 3. Все интерактивные элементы — минимум 44 px на телефоне. Системный шрифт.

**Матрица ролей.** Таблица роли × права с переключателями; вкладка персональных исключений: пользователь, право, grant/deny, кто и когда выдал, **срок действия** (новое поле `user_capabilities.expires_at`, серверная проверка в `hasCapability` игнорирует просроченные). Новое право **`survey:fill`**, по умолчанию у всех шести ролей; маршруты `/survey/*` закрываются им.

## 6. Этап 1 — сбор данных

**Список подразделений.** Свои подразделения (по роли), у каждого одна метрика: «решено N из M должностей», статусный бейдж. C&B/админ видят все с поиском.

**Экран подразделения.** Один список должностей из штатки. Карточка: название, до трёх компаний, бейдж одного из четырёх состояний (не начата / не с кем / в работе «12 из 40» / заполнена «40 из 40»). Вся карточка кликабельна. Фильтр-чипы по состоянию и поиск — только если должностей больше трёх. В шапке один индикатор прогресса.

**Лист заполнения** (маршрут `/new/survey/:unit/:position`). Шапка: должность, **валюта один раз** (по умолчанию сомони, не наследуется). Слева/сверху на телефоне — список компаний со статусом и кнопка «Добавить компанию». Справа — карточка компании с блоками: Оклад → График → Премии → Льготы → Откуда данные → Комментарий. Раскрыт только первый незаполненный; автораскрытие следующего при заполнении текущего; ручное закрытие уважается (флаг в состоянии формы). Сохранение карточки — кнопкой, валидация по единому контракту (раздел 8) до отправки.

**Шторка выбора компаний.** Открывается из листа. Чек-лист: пул подразделения + справочник холдинга по релевантности, поиск, добавление новой на лету (`survey/dictionary/add`). Каждый чек сохраняется сразу (`survey/position-selection/save`), компания сразу появляется в списке листа.

**«Сравнивать не с кем».** Кнопка на карточке должности и в листе. Обратима: добавление компании снимает отметку. Хранение — см. раздел 7.

**Смежные группы.** Перед сохранением в подразделении с `group_key` — подтверждение «данные уйдут на N площадок: …» с возможностью отказаться (тогда сохраняется только в текущее).

**Прогресс** — расчёт в `domain/progress.ts`, один на все экраны, с тестами:
- запись: 9 пунктов из ТЗ 3.4;
- компания: заполнена, если есть оклад, размер бонуса, льготы, прочие выплаты или комментарий;
- должность: решена, если есть ≥1 заполненная компания или отметка «не с кем»;
- подразделение: доля решённых должностей.

## 7. Точечные правки сервера

1. **Отметка «не с кем».** Новая таблица `position_no_comparison (unit, period_id, pos_our, marked_by, marked_at, UNIQUE(unit, period_id, pos_our))`. Маршруты `POST /survey/no-comparison` (поставить) и `POST /survey/no-comparison/clear` (снять); `savePositionSelection` с непустым списком снимает отметку сам. `getPositionSelections` возвращает дополнительно `noComparison: string[]`. Разнос по смежной группе — как у выбора компаний.
2. **Прогресс по должностям.** В `analyticsService.js` — функция `positionProgress(unit, periodId)`: решено/всего; используется в ответе `survey/for-period` (поле `progress`) и в дашборде «Прогресс». Старая метрика по компаниям остаётся.
3. **Право `survey:fill`** в `capabilities.js`, по умолчанию всем ролям; `requireCapability('survey:fill')` на `/survey/*`.
4. **`user_capabilities.expires_at`** — колонка, учёт в `hasCapability`, поле в GET/POST `admin/user-capabilities`.
5. **Отдача `/new`** в `server.js`: статика `client/next` + fallback на `index.html`.
6. **Валидация на сервере** (ТЗ раздел 11): в `saveSurveyDetails` график, наличие бонусов, источник и надёжность обязательны для начатой записи; валюта и период только из справочника — ошибка вместо подмены. Правила описаны в `src/services/surveyValidation.js` и продублированы 1:1 в `web/src/domain/validation.ts`; серверные тесты и клиентские тесты гоняют один и тот же набор кейсов из общего JSON-файла `test/fixtures/surveyValidation.json`.

Схема БД в остальном не меняется, данные не мигрируют.

## 8. Валидация — единый контракт

Правила из ТЗ 11, в одном месте на каждой стороне, с общим набором тест-кейсов:

- компания, наша должность — обязательны;
- оклад от/до — число с разделителями пробел/запятая/точка, ≥ 0, ≤ 1 000 000 000, «от» ≤ «до»;
- валюта, период выплаты — только из справочника;
- график, наличие бонусов, источник, надёжность — обязательны для начатой записи (где заполнено хоть что-то);
- остальное — обрезка пробелов.

Клиент показывает ошибки под полем и не отправляет запрос; сервер возвращает `{ ok:false, error, fields: { field: 'текст' } }`, клиент раскладывает по полям.

## 9. Обработка ошибок и состояния

- Загрузка — скелетоны, не спиннер на весь экран.
- Ошибка сети/сервера — тост с текстом сервера и кнопкой «Повторить» там, где повтор безопасен (чтение).
- Сохранение — кнопка блокируется на время запроса; успех — короткий тост; конфликт «запись принадлежит другому» — сообщение сервера как есть.
- Оффлайн в Mini App — баннер «нет связи», кнопки сохранения недоступны.

## 10. Тестирование

- `domain/*` — юнит-тесты на все ветки (прогресс, валидация, валюта).
- Компоненты дизайн-системы — smoke-тесты рендера и доступности (роль, имя).
- Экраны — тесты ключевых сценариев с замоканным API: добавить компанию из листа → заполнить → «готово»; «не с кем» → снятие; валидация не даёт отправить.
- Серверные правки — `node --test` на новые маршруты и валидацию.
- Ручная сквозная проверка по ТЗ раздел 15 на ширине 375 px и десктопе, консоль без ошибок.

## 11. Порядок работ

1. Каркас `web/` (Vite, TS, Query, Router), отдача `/new`, деплой-скрипт.
2. Дизайн-система и тема.
3. Слой API и типы контракта.
4. Вход, сессия, оболочка, навигация по правам.
5. Сервер: `survey:fill`, `expires_at`, отдача `/new`.
6. Матрица ролей.
7. Сервер: «не с кем», прогресс по должностям, валидация.
8. Домен: прогресс, валидация (с общими фикстурами).
9. Список подразделений, экран подразделения.
10. Лист заполнения, шторка компаний, «не с кем», смежные группы.
11. Сквозная проверка, телефон, консоль.

Каждый шаг заканчивается работающим приложением и локальным коммитом. На прод не пушится без отдельной просьбы.
