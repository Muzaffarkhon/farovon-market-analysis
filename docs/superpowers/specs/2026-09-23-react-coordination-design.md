# Дизайн: этап 4 — координация для HR BP (новый клиент)

Дата: 2026-09-23. Ветка `redesign/react`. Продолжение
`2026-09-23-react-dashboard-design.md`. Источник требований —
`docs/ТЗ_переписывание_интерфейса_2026-09-22.md`, раздел 1.4 (модульного
раздела с таким названием в ТЗ нет — только упоминание в разделе 14 и
описание экрана в 1.4).

## 1. Зачем

Раздел 1.2 ТЗ прямо ставит HR BP в роль координатора, а не контролёра:
«видит прогресс, дожимает отстающих, отвечает на вопросы». Сегодня для этого
нет отдельного экрана — есть только `/dashboard/hrbp` (таблица подразделений
внутри старого дашборда) и сломанная кнопка массового напоминания в боте
(шлёт по устаревшему флагу `competitors.actual`, упразднённому вместе со
старым Шагом 1 — см. `docs/archive/HANDOFF_2026-09-22.md`).

Раздел 1.4 описывает пять вещей, которых сегодня нет ни в одном виде:
прогресс по направлениям, список **людей** с их охватом (не только
подразделений), должности без решения отдельно от нерешённых, точечное
напоминание выбранным людям, лента последних записей.

## 2. Область видимости

Новая capability `coordination:view` (`src/config/capabilities.js`) —
отдельная от `dashboard:view`, потому что список ролей не совпадает:
раздел 1.4 называет «HR BP, руководителя направления, C&B, администратора»,
а `dir_head` (руководитель направления) сегодня **не** имеет
`dashboard:view` по умолчанию. Дефолты: `hrbp` и `dir_head` — да, `head`
(начальник отдела) и `user` — нет (они координируют не направление, а
работают внутри своего отдела — им экран не нужен). `cb` получает всё
автоматически (`CAPABILITIES.map(...)`), `admin` — как везде, в обход
проверки.

Видимость данных — тот же предикат, что у дашборда и реестра
(`unitScopeFilter` из `scopeService`): HR BP видит закреплённые направления,
руководитель направления — свои отделы, C&B/admin — весь холдинг.

## 3. Сервер

### 3.1 Новый сервис вместо второй копии логики `getHRBPDashboard`

`dashboardController.getHRBPDashboard` не трогается — старый клиент ходит
туда, как и раньше. Новый расчёт — `src/services/coordinationService.js`,
массово (без запроса на каждое подразделение — `positionProgressForUnit`
для этого не годится, три запроса на юнит при 326 юнитах слишком дорого):
те же bulk-запросы, что уже пишет `getHRBPDashboard` (`unit_positions`,
`position_company_selections`, `surveys`, `position_no_comparison`),
сгруппированные в памяти.

### 3.2 `GET /api/coordination` — прогресс по направлениям

Ответ:
```
{ ok: true,
  units: [{ unit, dir, hrbp, resp, head, positionsTotal, positionsDecided,
            state: 'не начато'|'в процессе'|'полностью', lastActivityAt }],
  people: [{ login, fio, units: string[], positionsTotal, positionsDecided,
             lastLoginAt, hasTelegram }],
  feed: [{ unit, dir, company, posOur, by, at }] // последние 30 по видимым направлениям
}
```

- **`units`** — как в `getHRBPDashboard`, но `positionsTotal`/`positionsDecided`
  вместо `posTotal`/`posFilled` (то же самое, имя приведено к общему словарю
  с дашбордом) и без устаревших `total`/`done`/`ask` (пары «должность × компания»
  — это заботa реестра и дашборда, не координации).
- **`people`** — новое. Каждый активный пользователь с непустым `users.units`
  (тем же полем, что уже читают `gradingController`/`telegramController`) или
  являющийся `resp`/`head` видимого подразделения. `positionsTotal`/
  `positionsDecided` — сумма по всем его подразделениям (без задвоения, если
  подразделение и в `units`, и он там же `resp`). `lastLoginAt` —
  `users.last_login_at` (уже пишется при входе, `authController.js:616`).
- **`feed`** — последние 30 записей `surveys` по видимым направлениям,
  `created_at desc`: подразделение, компания, наша должность, кто внёс,
  когда. Не таблица реестра (там полный набор колонок и фильтров) — просто
  «жив ли процесс», ссылки на реестр для деталей нет смысла дублировать.

### 3.3 «Отдельно — должности без решения»

Не отдельный запрос — производное от `positionsTotal - positionsDecided`
на уровне подразделения; на экране это фильтр/сортировка по разнице, не
новая агрегация. Раздел 3.1 ТЗ уже различает «не с кем» (осознанно) и
незаполненную (забыли) на уровне одной должности — здесь достаточно
не путать 0 из 0 (в подразделении вообще нет штатки) с N из N, где N > 0
(решено полностью).

### 3.4 `POST /api/coordination/remind` — точечное напоминание

Тело: `{ logins: string[] }`. Для каждого логина: если нет `telegram_chat_id`
— пропуск; иначе считается его личный охват (3.2, `people`) и, если есть
незакрытые должности, шлётся `sendTelegramMessage` с перечнем **его**
подразделений с незакрытыми должностями (не всего холдинга, как в сломанном
`sendMassReminder`). Ответ: `{ ok: true, sent, skipped }`.

**Сознательно не трогаем** `services/telegramService.sendMassReminder` —
она использует упразднённый флаг `competitors.actual` и уже отмечена в
хендоффе как сломанная; чинить массовую рассылку целиком, с идемпотентностью
и расписанием, — раздел 14 ТЗ, этап 7. Здесь — только точечная, по явно
выбранным на экране людям, из корректной модели данных.

## 4. Клиент

### 4.1 Маршрут и навигация

`/coordination` — «Координация», пункт меню виден при `coordination:view`
(рядом с «Дашборды»/«Реестр» в `NavItems.ts`).

### 4.2 Экран

- **Подразделения** — список/таблица с полосой прогресса
  (`positionsDecided`/`positionsTotal`), пометкой состояния и датой последней
  активности. Сортировка «сначала отстающие» по умолчанию.
- **Люди** — список с ФИО, охватом (`X из Y`), датой последнего входа;
  чекбоксы для выбора адресатов напоминания. Без Telegram — видно (`hasTelegram:
  false`), выбрать всё равно можно, но при отправке такой человек будет
  пропущен (сервер посчитает его в `skipped`, клиент покажет предупреждение
  до отправки, а не после).
- **Кнопка «Напомнить»** — активна при ≥1 выбранном, после отправки —
  тост «Отправлено N, пропущено M (нет Telegram или уже всё закрыто)».
- **Лента** — последние 30 записей, без фильтров и пагинации (это не
  реестр); ссылки на реестр/анкету не нужны — назначение ленты чисто
  индикативное («процесс живой»).
- Общий фильтр направления — как на дашборде, для тех, у кого направлений
  больше одного (C&B, admin).

### 4.3 Загрузка

TanStack Query, один запрос на весь экран (`/api/coordination` отдаёт все
три блока разом — они у координатора почти всегда нужны вместе, отдельные
запросы добавили бы только сетевые накладные расходы). Пустое состояние —
если `units` пуст (нет закреплённых направлений).

## 5. Тесты

- `coordinationService` — `node --test`, на синтетических `divisions`/
  `unit_positions`/`surveys`/`users` (как у `registryService.test.js`,
  без обращения к реальной базе): подразделение без штатки не даёт «0 из 0»
  как «полностью»; человек с двумя подразделениями не задвоен, если он и
  `resp`, и в `users.units`; лента отсортирована по дате; область видимости
  по роли (hrbp видит только свои направления).
- Маршруты — доступ без `coordination:view` отдаёт 403; `remind` пропускает
  людей без Telegram и с закрытым охватом, не считает их отправленными.
- Клиент — `vitest`: список подразделений и людей рендерится; выбор людей и
  отправка напоминания уходит с правильным списком логинов; пункт меню
  скрыт без права.

## 6. Чего здесь нет

Массовой автоматической рассылки, идемпотентности бота, подписи Mini App,
расписания напоминаний — раздел 14 ТЗ, этап 7 (и починка `sendMassReminder`
там же). Назначения/смены ответственных (`resp`/`head`/`hrbp` подразделения)
— это оргструктура, этап 6 «Администрирование». Оценки должностей и рисков
ключевого персонала — отдельные разделы навигации, не эта вкладка (этап 5).
