# Дизайн: этап 2 — реестр собранных данных (новый клиент)

Дата: 2026-09-23. Ветка `redesign/react`. Продолжение
`2026-09-22-react-stage0-1-design.md`.

## 1. Зачем

Реестр — единственное место, где видно **каждое** наблюдение целиком: кто, когда,
по какой компании и должности, с какой вилкой, переменной частью, льготами,
графиком, источником и надёжностью. Сегодня он живёт вкладкой внутри дашборда в
старом клиенте: данные приходят внутри тяжёлого ответа `/dashboard/extended`
(вся аналитика сразу), фильтруются наполовину на сервере, наполовину в браузере,
пагинация по 50 строк — в памяти. Колонок «надёжность», «грейд», «график» в
таблице нет вовсе, хотя в анкете они собираются.

В новом клиенте реестр — самостоятельный раздел со своим маршрутом, своим лёгким
эндпоинтом и полным набором колонок и фильтров.

## 2. Область видимости

Право — `dashboard:view` (то же, что у аналитики: реестр показывает те же
наблюдения, только построчно). Ограничение по подразделениям — тот же предикат,
что у дашборда (`dashboardUnitFilter`): admin и C&B видят весь рынок, HR BP — свои
подразделения, руководители — закреплённые. Предикат переезжает из
`dashboardController` в `services/scopeService.js`, чтобы два контроллера не
расходились.

## 3. Сервер

### 3.1 Эндпоинт

`POST /api/registry` — `requireCapability('dashboard:view')`.

Запрос:

```
{ period?, dir?, hrbp?, region?, unit?, company?, posOur?, source?, trust?,
  schedule?, cur?, grade?, bonHas?, search?, onlyUnmapped?, sort?, order?,
  page?, perPage? }
```

Ответ:

```
{ ok: true, rows: [...], total, page, perPage, period: {id, name},
  facets: { dirs, hrbps, regions, units, companies, sources, trusts,
            schedules, currencies, grades }, scoped }
```

Строка реестра — ровно то, что собирает анкета, плюс связанное с подразделением:

`id, date, by, dir, unit, region, company, posOur, posTheir, grade, payFrom,
payTo, cur, payPer, bonHas, bonuses[], varPay, benefits[], extra, schedule,
source, trust, note`.

### 3.2 Почему отдельный сервис, а не `getExtendedAnalytics`

Аналитика считает медианы, вилки, гистограммы, рейтинги компаний — реестру из
всего этого нужны только сырые строки. Гонять полный расчёт ради одной страницы
в 50 строк дорого и хрупко (любая правка аналитики ломает реестр). Поэтому
`services/registryService.js` читает `surveys` + `divisions` за выбранный период,
склеивает направление/регион/HR BP, применяет фильтры, считает грани (facets) и
режет страницу. Разбор переменной части и льгот переиспользуется из
`analyticsService` (`parseBonusesCol`, `summarizeVarPay`) — вторая реализация
разошлась бы с дашбордом.

### 3.3 Грани фильтров

Считаются по строкам, видимым пользователю **после** ограничения по правам, но
**до** применения самих фильтров — иначе выбранное значение исчезает из своего же
списка. Пустые значения в грани не попадают.

### 3.4 Сортировка

Белый список полей: `date, company, posOur, payFrom, payTo, unit, dir, trust,
source, by`. Всё остальное — `date desc`. Порядок — `asc`/`desc`. Сортировка на
сервере, чтобы страница была страницей общего порядка, а не порядка внутри
страницы.

### 3.5 Экспорт

`POST /api/registry/export` с теми же фильтрами, без пагинации, отдаёт CSV
(разделитель `;`, BOM — Excel на Windows). Факт выгрузки пишется в `audit_log`
тем же способом, что `logExport` (кто, когда, IP, сколько строк, какие фильтры) —
этого требует раздел ТЗ о безопасности, и так уже устроен экспорт дашборда.

## 4. Клиент

### 4.1 Маршрут и навигация

`/registry` — «Реестр данных», пункт меню виден при `dashboard:view`.
Фильтры и страница живут в query-параметрах адреса: ссылку на отфильтрованный
реестр можно переслать, «назад» возвращает предыдущий фильтр, F5 ничего не теряет.

### 4.2 Экран

- **Панель фильтров.** Строка поиска (компания, должность, кто собрал) плюс
  выпадающие списки граней. На узком экране панель сворачивается в кнопку
  «Фильтры» со счётчиком активных. Рядом — «Сбросить», когда что-то выбрано.
- **Таблица** на широком экране: дата, направление, подразделение, компания,
  регион, наша должность, должность у них, грейд, оклад от/до, валюта и период,
  переменная часть, льготы (число), график, источник, надёжность, кто собрал.
  Прилипшая шапка, сортировка кликом по заголовку.
- **Карточки** на узком экране вместо таблицы — та же выдача, сокращённая до
  компании, вилки, должности, направления и даты.
- **Пагинация** снизу: страница, всего страниц, «сколько показано из скольких».
- **Карточка наблюдения** — шторка сбоку по клику на строку: все поля, включая
  льготы списком, все виды переменной части, примечание. Из карточки — переход
  к анкете этой компании (`/survey/:unit/:position`), если есть право `survey:fill`.
- **Пустые состояния** различаются: «ничего не найдено» при фильтрах (с кнопкой
  сброса) и «за период ещё ничего не собрано» на чистом реестре.

### 4.3 Загрузка

TanStack Query, ключ — нормализованный объект фильтров. `placeholderData:
keepPreviousData`, чтобы таблица не мигала при листании. Дебаунс поиска — 300 мс.

## 5. Тесты

- `registryService` — `node --test`: фильтры (каждый по отдельности и вместе),
  грани считаются до фильтров, сортировка по белому списку, пагинация, область
  видимости по роли, CSV-экранирование.
- Маршрут — доступ без `dashboard:view` отдаёт 403.
- Клиент — `vitest`: фильтр уходит в запрос и в адрес; сортировка кликом;
  пагинация; карточка наблюдения открывается и закрывается; пустые состояния
  различаются; сброс фильтров.

## 6. Чего здесь нет

Редактирования записей из реестра (правка — в анкете), сравнения с рынком (это
дашборды, следующий этап), сопоставления должностей (это бенчмаркинг). Реестр
только показывает и выгружает.
