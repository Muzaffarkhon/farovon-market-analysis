# Дизайн: этап 6 — администрирование (новый клиент)

Дата: 2026-09-23. Ветка `redesign/react`. Продолжение
`2026-09-23-react-grading-design.md`. Источник требований —
`docs/ТЗ_переписывание_интерфейса_2026-09-22.md`, раздел 14 (этап 6) и
раздел 9 (администрирование).

## 1. Зачем

Последний из «функциональных» этапов: экраны, которые настраивают систему,
а не заполняют/смотрят данные. Сюда же по плану стягивается всё, что
предыдущие этапы сознательно откладывали как административную настройку:
импорт/сопоставление бенчмарка (этап 3), правка формулировок анкеты и
состав блоков/комиссии грейдирования (этап 5), импорт справочника
сотрудников (упоминался с самого начала как «этап 6»).

Все нужные серверные маршруты уже существуют и покрыты серверными тестами
— см. исследование ниже. Единственное исключение — списка периодов нет
отдельным JSON-эндпоинтом (есть только «текущий активный»), для него
нужен один новый маленький маршрут.

## 2. Область видимости

Шесть областей, каждая — отдельный экран/группа экранов под своим правом:

| Область | Право(а) | Маршрут |
|---|---|---|
| Пользователи | `users:view`/`users:create`/`users:edit` | `/admin/users` |
| Роли и доступы | роль `admin` | `/access` (уже реализовано этапом 4, без изменений) |
| Оргструктура | `divisions:view`/`divisions:edit` | `/admin/divisions` |
| Справочник сотрудников | `dictionary:view`/`dictionary:create`/`dictionary:edit`, импорт — `service:edit` | `/admin/staff` |
| Грейдирование — настройка | `grading:factors`/`grading:blocks`/`grading:committee` | `/admin/grading` |
| Бенчмаркинг — импорт и сопоставление | `benchmarks:import`/`benchmarks:map` | `/admin/benchmark` |
| Периоды сбора | `period:view`/`period:edit` | `/admin/periods` |

Общий вход — пункт меню «Администрирование» (виден при наличии хотя бы
одного из перечисленных прав, либо роли `admin`), ведёт на `/admin` —
список карточек-разделов, видны только те, на которые есть право (как
карточки блоков грейдирования). Каждый раздел — самостоятельный маршрут,
не вложенные вкладки одного монолитного компонента: так разделы можно
открывать напрямую по ссылке и лениво грузить.

`/access` остаётся отдельным пунктом верхнего уровня (уже был на этапе 4),
но также появляется карточкой на `/admin` для единообразия — это чисто
навигационное дублирование, компонент один и тот же.

## 3. Сервер

Почти не меняется — см. таблицу маршрутов ниже. Единственное дополнение:

### 3.1 Новый маршрут: список периодов

`GET /api/admin/periods` (право `period:view`) — тонкая обёртка над
таблицей `periods`, которой сегодня нет: `getActivePeriod()` отдаёт только
активный период, `period-grants` привязан к активному. Нужен список всех
периодов для выпадающего списка/таблицы управления.

Ответ: `{ ok, rows: [{ id, name, state, fromDate, toDate, isActive,
updatedBy, updatedAt }] }`, сортировка по `id DESC`.

Файлы: `src/controllers/adminController.js` (новая функция
`listPeriods`), `src/routes/api.js` (маршрут), `test/adminController` —
если для соседних admin-маршрутов есть unit-тесты на контроллер, добавить
рядом; если проверка только интеграционная — тест на pure-функцию выборки
(если есть смысл её выделять) или ручная проверка через curl/браузер,
как для остальных admin-маршрутов в этом контроллере (в файле нет чистых
функций для большинства из них — не создаём искусственную абстракцию
ради одного маршрута).

### 3.2 Существующие маршруты (без изменений)

## 4. Клиент — по разделам

### 4.1 `/admin` — хаб

Карточки разделов (та же визуальная схема, что `BlocksList` у
грейдирования): название, короткое описание, видимость по праву.
`useSessionData()` уже даёт `user.role`/`capabilities` — фильтрация та же
функция стиля `navItemsFor`.

### 4.2 `/admin/users` — пользователи

- Таблица: ФИО, логин, роль, подразделения, телефон, должность, статус
  (активен/выключен), последний вход, значок Telegram (`hasTelegram`).
  Фильтр по роли и по тексту (клиентский, как в реестре).
- Кнопка «Добавить» → шторка: ФИО, роль (`Select` из `ROLE_LABELS` —
  нужен статический список либо запрос ролей у `/access`, см. 4.6 —
  переиспользовать оттуда, не дублировать), телефон, должность,
  подразделения (мультивыбор из `divisions`), активен. Логин генерируется
  сервером при создании (не поле формы) — сервер сам решает `create`/`edit`
  по наличию `login` в теле; для новой записи это поле просто не
  отправляется.
- Кнопка на строке: «Сбросить пароль» (вызывает `reset-password`, показывает
  результат: доставлено в Telegram / не привязан Telegram / отказ) —
  подтверждение через `confirm`-шторку, необратимое действие с точки зрения
  пользователя (старый пароль перестаёт работать).
- Переключатель активности — `toggle`, с подтверждением на выключение
  (не на включение).
- Отдельная вкладка/фильтр «Архив» — `GET /admin/users-archive`,
  кнопка «Восстановить».

### 4.3 `/admin/divisions` — оргструктура

- Дерево/таблица по `dir` → `unit`, с полями `head`/`resp`/`hrbp`/`note`,
  флагами `is_survey_target`/`is_hidden`. Права по ролям уже разделены
  сервером (`dir_head`/`head` не могут менять `dir`/`group`/`region`) —
  клиент просто не показывает недоступные поля как редактируемые
  (`disabled`, не скрытие) для этих ролей, чтобы не создавать иллюзию, что
  поле можно было бы поменять.
- «Создать подразделение» (только admin/cb) — вызов `divisions/create`.
- «Переместить» — простая форма выбора нового `dir`/`parentUnit`, вызывает
  `divisions/move`.
- «Скрыть»/«Удалить» — `hide`/`delete`; `delete` может отказать (юнит
  используется) — показать текст ошибки сервера, не гадать заранее.
- «Массовое назначение по направлению» (`batch-assign`) — форма: направление
  + одно из полей `head`/`hrbp`/`resp` + значение → применяется ко всем
  юнитам направления. Это не часто используемая функция — один компонт
  формы, не отдельный экран.
- Автоподбор смежных групп (`adjacent-group`) — вне первой итерации этого
  таска, если время не позволит: это второстепенная функция поверх
  основного CRUD, и уже отмечена как проблемная в проде (см. память
  `farovon-fill-flow-todo` — `alignOrgBranches()` баг). Явно отметить в
  плане как «если останется время», не блокирует остальной раздел.

### 4.4 `/admin/staff` — справочник сотрудников

- Таблица `staff_directory`: подразделение, ФИО, должность. Поиск по ФИО.
  Ручное добавление/правка/удаление одной записи.
- «Импорт из CSV» — загрузка файла → сначала dry-run (`dryRun: true`,
  показывает отчёт: сколько строк, сколько подразделений не найдено, список
  несопоставленных) → кнопка «Подтвердить импорт» отправляет `dryRun:false`
  (полная замена таблицы — предупредить текстом, что это заменяет весь
  справочник целиком, а не добавляет).

### 4.5 `/admin/grading` — настройка грейдирования

Три под-раздела на одном экране (вкладки, без отдельных маршрутов — по
аналогии с `/dashboard`, но здесь проще: не завязано на фильтры):
- **Формулировки** — по блокам/направлениям: список семи факторов,
  правка `title`/`help`/`options[5]`/`examples[5]` для конкретного `dir`
  (`scope`/`idx`/`dir` в `saveFactor`) или сброс к оригиналу
  (`grading-factors/reset`).
- **Блоки** — список блоков + псевдо-блок «Не распределено»; таблица
  подразделение+должность → блок, с возможностью перенести
  (`grading-blocks/reassign`) и сбросить утверждённую оценку
  (`reset-evaluation`, с подтверждением — необратимо стирает результат).
- **Комиссия** — выбор блока → список членов, добавить/убрать по логину
  (поиск по ФИО среди пользователей, как в `/admin/users`), список
  «в ожидании кворума» и кнопка «Подвести итог принудительно»
  (`committee/finalize`, необратимо и подтверждение).

### 4.6 `/admin/benchmark` — импорт и сопоставление бенчмарка

- **Источники**: список (`sources`), создать/отредактировать (`title`,
  `kind`, `defaultCurrency`, `isLicensed`, `notes`), веса между источниками.
- **Импорт**: загрузка `.xlsx` → выбор листа (`xlsx-sheets`) → просмотр
  сетки и указание, какие столбцы что означают (`xlsx-grid` + ручной выбор
  колонок, `columnMap`) → dry-run (`import/dry-run`, показывает отчёт) →
  «Подтвердить» (`import/commit`). Это самый тяжёлый экран этапа — четыре
  шага мастера, есть смысл сделать отдельным компонентом-визардом
  (`BenchmarkImportWizard`) с внутренним стейтом шага, а не пятью разными
  маршрутами роутера.
- **Сопоставление позиций**: таблица источник↔справочник, автоподсказки
  (`suggest-mappings`), подтвердить/удалить сопоставление.
- **Наборы данных**: список датасетов с состоянием, удаление.

### 4.7 `/admin/periods` — периоды сбора

- Таблица периодов (новый `GET /admin/periods`): имя, статус, даты, кто
  и когда менял, отметка активного.
- «Новый период» (`action: new`) — с явным предупреждением: сбрасывает
  `actual` у всех наблюдений (текст ровно как в старом клиенте, если он
  там есть — проверить при реализации, не выдумывать формулировку заново).
- «Закрыть»/«Переоткрыть»/«Активировать прошлый»/«Редактировать» —
  оставшиеся `action`.
- «Удалить» — только для пустого периода (сервер и так откажет; клиент
  не блокирует кнопку заранее, чтобы не дублировать бизнес-правило, но
  показывает понятную ошибку сервера).
- Панель грантов на архивный период (`period-grants`) — отдельный блок:
  выбрать пользователя (`period-grants/users`), выдать/отозвать доступ на
  редактирование закрытого периода.

## 5. Общие визуальные примитивы

Новых примитивов, скорее всего, не потребуется — таблицы/шторки/формы уже
есть (`Sheet`, `Select`, `Input`, `Textarea`, `Button`, `Card`, `Badge`,
`Chip`). Единственный вероятный новый — `FileDrop`/файловый инпут для CSV
и xlsx (простая обёртка над `<input type="file">`, без drag-n-drop в первой
итерации — не требуется ТЗ).

## 6. Тесты

Как и на предыдущих этапах: серверный тест только для нового
`GET /admin/periods` (простая проверка сортировки/формы ответа). Остальное
— клиентские `vitest`-тесты по разделам: рендер таблицы по ответу API,
видимость по праву (как в `NavItems.test`), отправка формы вызывает
правильный метод API с правильными полями, dry-run-затем-commit для
импортных мастеров (справочник, бенчмаркинг) — два теста на мастер:
«dry-run показывает отчёт, кнопка подтверждения не отправляет данные»,
«после дан confirm вызывается commit с dryRun:false/соответствующим телом».

## 7. Порядок реализации (см. план)

Семь задач по числу разделов (хаб объединён с первой задачей): пользователи
→ оргструктура → справочник сотрудников → грейдирование-админ → бенчмаркинг
-импорт (самая тяжёлая) → периоды (+ новый серверный маршрут) → финальная
сквозная проверка. Порядок — от простого CRUD к самому сложному мастеру,
как и в предыдущих этапах.

## 8. Чего здесь нет

Правки самой методики (веса факторов грейдирования, пороги грейдов,
формула риска) — не входит в объём переписывания интерфейса. Security-фиксы
раздела 12 ТЗ и вывод старого клиента из эксплуатации — этап 9. Telegram-бот
и раздел поддержки — этапы 7–8.
