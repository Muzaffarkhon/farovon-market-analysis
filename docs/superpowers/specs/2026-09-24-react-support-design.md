# Дизайн: этап 8 — чат поддержки

Дата: 2026-09-24. Ветка `redesign/react`. Продолжение
`2026-09-24-react-bot-design.md`. Источник требований —
`docs/ТЗ_переписывание_интерфейса_2026-09-22.md`, раздел 9 (плюс раздел
14: «Поддержка: уведомления по web-тредам, инбокс»).

## 1. Зачем

Раздел 9 ТЗ называет главным дефектом то, что сотрудник, написавший из
интерфейса, не получает ответа вовремя — администратор просто не узнаёт о
сообщении, пока сам не откроет инбокс. Аудит кода подтвердил это и ещё
кое-что сверх формулировки ТЗ: уведомление не приходит на новые сообщения
в уже открытом треде **ни для одного** из двух каналов (бот тоже только
уведомляет при переоткрытии закрытого треда, а не на каждое сообщение — это
осознанный анти-спам компромисс в текущем коде, но слишком грубый: если
сотрудник за день написал 5 сообщений в новый тред, администратор узнает
только о первом).

Отдельно: в новом React-клиенте (`web/`) канала поддержки нет вовсе — ни
экрана «Написать в поддержку» для обычного сотрудника, ни админского
инбокса. Без первого нечем проверить исправление уведомлений (web-тред
неоткуда создать), без второго некому увидеть уведомление на экране.
Both — часть этого этапа, не только бэкенд.

## 2. Область видимости

Сервер: `src/services/supportChatService.js` (централизация уведомлений),
`src/controllers/myServiceController.js`, `src/db/migrate.js` (колонка
`notified_at`). `telegramController.js` — убрать три разрозненных вызова
`notifySupportTeam`, один точечный случай (открытие треда без первого
сообщения) оставить.

Клиент — два новых раздела:
- `/support` — «Поддержка», видно всем (как у `myServiceController` —
  никакого `requireCapability`, любой залогиненный).
- `/admin/support` — «Чат поддержки», карточка в `AdminHub`, видимость по
  `support:manage` (уже существующая capability, ничего не меняется в
  правах).

## 3. Сервер

### 3.1 Уведомления — один throttled путь вместо трёх разрозненных

Раньше: `notifySupportTeam` вызывался по обстоятельствам в трёх местах
`telegramController.js` (не найден номер, открытие треда гостем,
переоткрытие закрытого) и нигде в `supportChatService.js`/
`myServiceController.js` — отсюда и дыра с web-тредами.

**Новое.** Один центр принятия решения — `supportChatService.js`:

```js
const NOTIFY_THROTTLE_MS = 5 * 60 * 1000; // 5 минут

async function maybeNotifySupportTeam(threadId) {
  const thread = await queryOne(
    `SELECT t.id, t.phone, t.source, t.topic, t.notified_at, t.telegram_chat_id, u.fio AS user_fio
     FROM support_threads t LEFT JOIN users u ON u.id = t.user_id WHERE t.id = ?`,
    [threadId]
  );
  if (!thread) return;
  const last = thread.notified_at ? new Date(thread.notified_at).getTime() : 0;
  if (Date.now() - last < NOTIFY_THROTTLE_MS) return;

  await run('UPDATE support_threads SET notified_at = ? WHERE id = ?', [new Date().toISOString(), threadId]);

  const { notifySupportTeam } = require('./telegramService');
  const who = thread.source === 'web'
    ? (thread.user_fio ? escHtml(thread.user_fio) : 'Сотрудник (не найден)')
    : (thread.phone ? `номер ${escHtml(thread.phone)}` : `chat ${thread.telegram_chat_id}`);
  await notifySupportTeam(
    `💬 <b>Новое сообщение в чате поддержки</b>\n${who}\nОткройте раздел «Чат поддержки» в системе.`
  );
}
```

Throttle по `notified_at` (не по `last_message_at`) — новый тред всегда
проходит (`notified_at IS NULL`), а быстрая переписка не заваливает
admin/cb сообщениями чаще раза в 5 минут на тред. Это одновременно
заменяет прежнее правило «только на открытие/переоткрытие» (более грубое
и теперь избыточное) и закрывает дыру с web-тредами — один механизм на
оба канала.

Точки вызова — везде, где в тред падает новое **входящее** сообщение (не
исходящее от админа):
- `saveIncomingMessage` (бот, оба сценария — новый тред и продолжение) —
  добавить вызов в конце.
- `createWebThread` (первое сообщение сотрудника) — вызвать после вставки.
- `saveOwnMessage` (сотрудник пишет в уже созданный тред) — вызвать в конце.

Один оставшийся частный случай — `openSupportThreadForGuest`
(`telegramController.js`): гость нажал «Написать администратору», треда
ещё нет, но и сообщения ещё нет тоже (текст придёт следующим апдейтом).
Здесь по-прежнему отдельный явный вызов `supportChat.maybeNotifySupportTeam(threadId)`
сразу после `getOrCreateThread` — единственное место вне трёх функций
записи сообщений.

Убрать: три точечных вызова `notifySupportTeam` в `telegramController.js`
(`handleContact` — номер не найден, `handleSupportMessage` — переоткрытие)
и комментарий про антиспам-компромисс — он больше не описывает код.

### 3.2 Схема

`ensureColumn('support_threads', 'notified_at', 'DATETIME')`.

### 3.3 Новый серверный маршрут не нужен

Все существующие эндпоинты (`myServiceController`, `supportController`) уже
покрывают и старый, и новый клиент — контракт не расширяется, кроме
чтения `notified_at` (внутреннее поле, наружу не отдаётся).

## 4. Клиент

### 4.1 `/support` — «Поддержка» (обычный сотрудник)

Пункт меню виден всем, без проверки прав (`NavItems.ts`, как раздел
«Сбор данных» — просто без условия `has(...)`).

Экран одностраничный:
- Если открытых тредов нет — форма «Написать в поддержку»: тема (до 100
  символов) + текст (до 2000) → `myServiceApi.start(topic, text)`.
- Если тред есть — переписка (входящие/исходящие пузырьки, как в
  админке, но без панели инструментов), поле ответа снизу.
- Блок «Частые вопросы» под перепиской — сворачиваемые вопрос/ответ из
  `GET /support/faq`, тот же справочник, что ведёт админка.
- Поллинг открытого треда — 20 секунд (то же значение, что уже
  используют оба таймера старого клиента, `mySupPollTimer`).

### 4.2 `/admin/support` — «Чат поддержки» (карточка в `AdminHub`,
`support:manage`)

Двухколоночный экран (список + детали), на узком экране — список,
переход в детали и кнопка «Назад» вместо raw-сплита:

- **Список.** Поиск (по ФИО/телефону/теме/тексту, `q` — уходит на сервер,
  не фильтруется в браузере), фильтры «Открыт/Закрыт», «Ждут ответа»,
  «Без привязки», «Только непрочитанные», переключатель «Архив»
  (`support:manage`-роль admin видит кнопку архива/удаления — как в
  старом клиенте, эти два действия остаются `requireRoles('admin')` на
  сервере, клиент прячет кнопки для cb). Строка — источник (сайт/Telegram),
  имя/«Гость #N»/«Сотрудник #N», превью последнего сообщения, время,
  бейдж непрочитанных.
- **Детали.** Шапка (привязанное ФИО/телефон/тема/статус), кнопки
  «Привязать к сотруднику» (скрыта для web-тредов — они уже привязаны по
  `user_id`), «Закрыть», «Архив»/«Удалить» (admin). Переписка + поле
  ответа с подсказкой готовых фраз (`support:manage`, `audience=admin`).
- **Привязка к сотруднику** — поиск по ФИО, список совпадений с
  телефоном, подтверждение (предупреждение о переносе Telegram, если уже
  привязан к другому) → `linkEmployee`, сервер сам высылает временный
  пароль.
- **Настройки** (готовые фразы для админов, вопросы-кнопки для гостей и
  ответы на них, FAQ) — значок-шестерёнка в шапке списка открывает Sheet
  с тремя вкладками (по образцу `admin/grading` — там уже три вкладки в
  одном экране). Не отдельный маршрут `/admin` — это настройка самого
  раздела «Чат поддержки», логичнее в его собственной шапке, чем в общем
  хабе администрирования.
- Поллинг списка — 20 секунд, тот же интервал, что у старого клиента
  (`supPollTick`).

### 4.3 Загрузка

TanStack Query, ключ — нормализованные фильтры (как у реестра). Список и
открытый тред — раздельные запросы (тред может быть открыт долго, не
нужно перезапрашивать весь список ради одного сообщения) — `refetchInterval`
на обоих, 20с.

## 5. Тесты

- `supportChatService.maybeNotifySupportTeam` — `node --test` с мок-БД
  (`queryOne`/`run` подменяются, как принято в тестах сервисов этого
  файла, если такие уже есть — иначе на синтетических объектах через
  прямой вызов throttle-логики, вынесенной в чистую функцию
  `shouldNotify(notifiedAt, now)` отдельно от похода в БД): свежий тред
  (`notified_at` пуст) — уведомляет; тред, уведомлённый 1 минуту назад —
  не уведомляет повторно; уведомлённый 6 минут назад — уведомляет снова.
- Маршруты — `/support/*` без сессии — 401; `/admin/support/*` без
  `support:manage` — 403.
- Клиент — `vitest`: сотрудник без треда видит форму создания, с тредом —
  переписку; админ видит список, применяет фильтр, открывает тред,
  привязывает к сотруднику; пункт «Поддержка» виден всем ролям в
  `NavItems.test.ts`.
