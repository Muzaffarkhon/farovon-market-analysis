# Предложение: модуль «Пересмотр заработной платы» (заявка → комиссия → 1С)

Статус: **согласован по ключевым вопросам** 22.09.2026, ждёт подтверждения на старт реализации. Ответы заказчика внесены в разделы 4, 5 и 9.

---

## 1. Как это устроено в мировых системах — и что берём

Смотрели три эталона: Workday (процесс «Request Compensation Change»), SAP SuccessFactors (off-cycle compensation worksheet) и Oracle HCM (salary change with approval rules). Общие черты, которые везде считаются стандартом:

| Практика | Где встречается | Берём? |
|---|---|---|
| **Код основания** (reason code): повышение, окончание стажировки, рыночная корректировка, удержание/контр-оффер, выравнивание, уникальный случай | все три | да — это и есть ваше «исключение», только формализованное списком |
| **Правила допуска** (eligibility): «последний пересмотр < N месяцев → недопустимо», с возможностью исключения по коду основания и обязательным обоснованием | SuccessFactors, Workday | да — ровно ваше правило 6 месяцев |
| **Compa-ratio и положение в вилке**: текущий и предлагаемый оклад показываются как % от середины вилки и как позиция внутри «от–до» | все три | да — это главный инструмент проверяющего: видно, что предлагают 130% от рынка, а не абстрактную цифру |
| **Совокупное вознаграждение**: оклад + каждая переменная часть отдельной строкой, итого в месяц и в год | все три | да |
| **Одна заявка — много сотрудников** (worksheet): планировщик заполняет таблицу, каждый сотрудник — колонка/строка, решение по каждому отдельно | SuccessFactors | да — ваше требование дословно |
| **Возврат на доработку** (send back) с комментарием, история видна всем участникам маршрута | Workday, Oracle | да |
| **Условная маршрутизация**: шаг пропускается, если выполнено условие (сумма ниже порога, тип заявки) | Workday | да — «стажировка → после HRD сразу к кадровику» |
| **Дата вступления в силу** (effective date) — обязательное поле | все три | да, иначе кадровику нечего вносить в 1С |
| **Передача в payroll/HRIS** отдельным финальным шагом с ограниченным экраном | все три | да — ваш кадровик и 1С |
| **Голосование комиссией** большинством | редко: в Workday согласование последовательное; голосование есть в комитетах по вознаграждениям топ-менеджмента и в корпоративных «comp committee» | да, по вашему требованию — с равными голосами и отзывом голоса |
| Бюджет на пересмотр (pool) и контроль его расхода | SuccessFactors, Workday | **пока нет** — не просили; можно добавить позже как «сколько уже одобрено за квартал» |
| SLA на шаг и авто-эскалация | Workday | **частично**: напоминание ботом через N дней без движения, без автоэскалации |

Ключевая мысль из мировой практики, которую стоит принять: **проверяющий должен видеть не цифру, а цифру в контексте** — вилка, рынок, compa-ratio, % роста, история пересмотров. Именно это делает решение комиссии быстрым и обоснованным.

## 2. Маршрут заявки

```
Черновик (HRBP)
   │  проверка допуска: последний пересмотр ≥ 6 мес ИЛИ есть код исключения + обоснование
   ▼
Проверка C&B ──── возврат на доработку ───► Черновик (с комментарием)
   │  C&B добавляет рыночные данные, проверяет полноту
   ▼
Согласование HRD ── отклонение (с комментарием) ──► Закрыта: отклонена
   │
   ├── тип «выход из стажировки» ─────────────────────────┐
   ▼                                                      │
Голосование комиссии (по каждому сотруднику)              │
   │  большинство «за» → одобрен; большинство «против» → отклонён │
   ▼                                                      ▼
Оформление в 1С (кадровик) ◄──────────────────────────────┘
   │  отмечает «внесено», указывает дату
   ▼
Закрыта: исполнена
```

Правила:

- **Допуск считается по каждому сотруднику**, не по заявке. Дата последнего пересмотра берётся из истории самой системы (после первой закрытой заявки) или вводится HRBP вручную для первого раза. Если меньше 6 месяцев и нет кода исключения — сотрудника **нельзя добавить** в заявку, система сразу пишет причину. С кодом исключения (контр-оффер, уникальный случай) и обоснованием — можно, но у сотрудника появляется пометка «исключение», которую видят все проверяющие.
- **Каждый шаг видит заявку только когда предыдущий её передал.** Пока C&B не отправил дальше, HRD её не видит. Реализуется просто: у заявки есть «текущий этап», и экран каждой роли фильтрует по нему.
- **Решения по сотрудникам независимы.** Комиссия голосует по каждому; отклонённый сотрудник выпадает из заявки, остальные идут дальше. Заявка закрывается, когда по каждому сотруднику есть финальное решение.
- **Отклонение и возврат — только с комментарием**, кнопка без текста не срабатывает.
- **Изменение состава заявки после отправки невозможно** — только возврат в черновик через C&B. Иначе комиссия голосует за одно, а видит другое.

## 3. Что в заявке

**Шапка заявки:** инициатор (HRBP, автоматически), направление/подразделение, тип заявки (плановый пересмотр / выход из стажировки / контр-оффер / уникальный случай), желаемая дата вступления в силу, документ-основание (протокол стажировки или иное — PDF/фото), общий комментарий.

**Таблица сотрудников** — сотрудники колонками, показатели строками (как просили). У каждой ячейки кнопка «→ скопировать вправо во все», чтобы не вбивать одинаковое:

| Строка | Кто заполняет | Откуда |
|---|---|---|
| ФИО, подразделение, должность | HRBP | выбор из справочника сотрудников (1С) |
| Дата последнего пересмотра | авто | история заявок; для первого раза — HRBP вручную |
| Текущий оклад | HRBP | вручную |
| Переменная часть — несколько строк: вид, размер (сумма или %), периодичность | HRBP | вручную, «+ добавить вид» |
| Текущее совокупное в месяц | авто | оклад + переменные, приведённые к месяцу |
| Предлагаемый оклад | HRBP | вручную |
| Предлагаемые изменения переменной части | HRBP | опционально |
| Рост, % | авто | |
| Вилка по должности «от–до» | авто | справочник должностей |
| Положение в вилке (сейчас / после) | авто | процент от «от» до «до» |
| Рыночная медиана и compa-ratio | **C&B** | из бенчмаркинга или вручную на шаге C&B |
| Код основания + обоснование | HRBP | список + текст; для исключений текст обязателен |
| Пометки: «исключение», «< 6 мес» | авто | |

**Документы:** до 5 файлов на заявку (PDF, JPG, PNG, до 10 МБ). Открываются **во всплывающей карточке поверх страницы** — просмотрел, закрыл, остался на месте. Хранилище — Vercel Blob (в проекте его пока нет, добавляется).

## 4. Роли и видимость

Новые права в матрице (роли не трогаем — назначаем права людям персонально или через роль):

| Право | Кто обычно | Что даёт |
|---|---|---|
| `comp:submit` | HRBP | создать заявку, видеть свои |
| `comp:review_cb` | C&B | шаг проверки, добавление рыночных данных, видеть **все** заявки во всех статусах |
| `comp:approve_hrd` | HRD — Сатторов Илхомчон Ахмадчонович | шаг согласования; ему же отдельно можно выдать `comp:vote`, тогда он и голосует в комиссии |
| `comp:vote` | члены комиссии | голосование; видят все заявки на этапе комиссии + свою историю голосований |
| `comp:payroll` | кадровик | только одобренные, только нужные поля |
| `comp:admin` | администратор | состав комиссии, кворум, принудительное закрытие |

Видимость заявки: инициатор, все, кто её уже касался или должен коснуться по маршруту, C&B, администратор. Остальные — не видят даже по прямой ссылке.

**Экран кадровика** намеренно урезан: ФИО, подразделение, должность, новый оклад, новые переменные части, дата вступления в силу, номер заявки, кнопка «Внесено в 1С». Никаких обоснований, голосов и комментариев.

## 5. Голосование комиссии

- Состав комиссии задаётся в админке (аналогично существующей комиссии по грейдированию — переиспользуем подход). HRD может входить в комиссию как обычный член.
- Голос: «за» / «против», по каждому сотруднику отдельно, с необязательным комментарием.
- Голос можно отозвать или изменить, пока по сотруднику не подведён итог.
- **Режим голосования переключается в настройках модуля**: «открытое» — члены комиссии видят голоса друг друга сразу; «закрытое» — до подведения итога видно только «проголосовал / нет», сами голоса раскрываются после. Переключение действует на новые заявки; уже идущее голосование режим не меняет.
- Итог подводится **автоматически**, когда достигнуто большинство **от состава комиссии** (не от проголосовавших). Состав фиксируется на момент передачи заявки комиссии; голоса выбывшего члена не учитываются.
- **Кто ещё не голосовал** — видно C&B и администратору на карточке заявки списком, независимо от режима. Не проголосовавшим система шлёт напоминание ботом через 3 дня и далее каждые 3 дня; C&B может нажать «Напомнить» вручную. Автоматического закрытия «по факту» нет — только администратор вручную.

## 6. Комментарии, история, уведомления

- Одна лента на заявку: действия (передал, вернул, проголосовал) и комментарии в хронологии. Видна всем участникам заявки. Удалить нельзя.
- Уведомления: Telegram-бот пишет тому, к кому заявка пришла на шаг, и инициатору при возврате/решении. В интерфейсе — счётчик на кнопке «Пересмотр ЗП»: сколько заявок ждут именно вашего действия.
- Реестр заявок с вкладками: **Ждут меня / Мои / Все актуальные / Закрытые**. Набор вкладок зависит от прав (кадровик видит только «Ждут меня» и «Исполнено»).

## 7. Данные (человеческим языком)

Появляются четыре сущности: заявка (шапка, статус, этап), строка сотрудника в заявке (все показатели, своё решение), переменная часть сотрудника (несколько на строку), событие ленты (кто, что, когда, комментарий, голос). Плюс состав комиссии и файлы. Существующие таблицы не меняются; справочник сотрудников и вилки используются на чтение.

Из закрытых заявок автоматически складывается **история пересмотров по сотруднику** — она и питает правило 6 месяцев в следующий раз, и даёт аналитике «сколько и кому подняли за год».

## 8. Место в общем плане переписывания

Рекомендация: **делать этот модуль первым экраном на новом стеке** (React, дизайн-система из ТЗ, этап 0). Причины:

1. У модуля нет старого интерфейса, с которым надо сохранять паритет — можно сразу делать правильно.
2. Он проверяет дизайн-систему на самом сложном экране (таблица с колонками-сотрудниками, шторки, карточка документа, лента).
3. Даёт бизнесу видимый результат раньше, чем переписанный «Сбор данных».

После него — этапы 1–9 из ТЗ по порядку.

## 9. Решения заказчика и принятые допущения

Зафиксировано 22.09.2026:

1. **HRD** — Сатторов Илхомчон Ахмадчонович; отдельным правом, при желании плюс право голоса в комиссии.
2. **Голоса комиссии** — режим переключаемый (открытое / закрытое), настройка модуля.
3. **Большинство** — от состава комиссии. Не проголосовавшие видны C&B, напоминания ботом; закрытие только вручную администратором.

Допущения исполнителя (не требовали ответа, можно поправить в любой момент):

4. **Рыночные данные на шаге C&B** подтягиваются автоматически из бенчмаркинга по сопоставленной должности, C&B подтверждает или правит вручную. Если сопоставления нет — поле пустое, заполняет C&B.
5. **Виды переменной части** — справочник (ведёт C&B), чтобы по ним собиралась аналитика. Начальный список: премия по KPI, премия за выработку, надбавка за вредность, надбавка за стаж, бонус за результат, прочее.
6. **Кадровик** — все, у кого есть право `comp:payroll`; уведомляются все, отмечает «внесено» один.
7. **Черновики** не удаляются автоматически; у инициатора в реестре есть кнопка удаления черновика.
