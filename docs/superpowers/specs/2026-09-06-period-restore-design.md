# Восстановление периода сбора — спецификация

Дата: 2026-09-06
Зависит от: PR #64 (`surveys.period_id`) — должен быть влит в `main` до начала.

## Задача

Два сценария, от которых сейчас нет защиты:

1. **Случайно нажали «Закрыть период»** — хотим просто открыть его обратно, тот же период, те же данные.
2. **Случайно нажали «Открыть новый период»** — теперь активен новый пустой период, а работа в прошлом не закончена. Хотим вернуть прошлый период как текущий.

Требование пользователя: делать «по-нормальному», через ID периода, без совпадения по названию — чтобы не было дублирования и путаницы между периодами с одинаковым именем.

## Как устроено сейчас

- «Текущий период» = **самая новая строка** таблицы `periods` (`SELECT * FROM periods ORDER BY id DESC LIMIT 1`). Так его определяют **16 мест** в коде.
- `apiSetPeriod` при **любом** действии делает `INSERT` новой строки:
  - Закрыть → INSERT строки (то же имя, `state = 'закрыт'`)
  - Открыть новый → INSERT строки (новое имя, `state = 'открыт'`)
- Анкеты (после PR #64) привязаны к периоду по номеру: `surveys.period_id → periods.id`.

### Почему нынешняя модель не даёт восстановление на ID

«Вернуть прошлый период» через вставку копии создаст **новую строку с новым `id`**. Анкеты, привязанные к `period_id` старой строки, окажутся отвязаны от «текущего» периода. Значит, восстановление на ID требует другого определения «какой период сейчас активен».

## Решение: явная отметка активного периода

Добавить `periods.is_active INTEGER NOT NULL DEFAULT 0`. Ровно одна строка в таблице имеет `is_active = 1` — это и есть текущий период сбора.

«Текущий период» больше **не** «самая новая строка», а `SELECT * FROM periods WHERE is_active = 1`.

### Операции

| Действие | Что делаем | Обратимо? |
|---|---|---|
| **Закрыть период** | `UPDATE periods SET state='закрыт', updated_by=?, updated_at=CURRENT_TIMESTAMP WHERE is_active=1` — правим ту же строку, новую не создаём | да, «Открыть закрытый обратно» |
| **Открыть закрытый обратно** (undo случайного закрытия) | `UPDATE periods SET state='открыт', updated_by=?, updated_at=CURRENT_TIMESTAMP WHERE is_active=1` — та же строка, все анкеты на месте | да |
| **Открыть новый период** | В одной транзакции (`batch`): `UPDATE periods SET is_active=0 WHERE is_active=1`, затем `INSERT INTO periods (name, state, is_active, ...) VALUES (?, 'открыт', 1, ...)`. Старый период сохраняет свой `id`, свои анкеты, свой статус | да, «Сделать активным снова» на старую строку |
| **Сделать активным снова** (undo случайного «Открыть новый», либо поднять любой архивный период) | В одной транзакции: `UPDATE periods SET is_active=0 WHERE is_active=1`, затем `UPDATE periods SET is_active=1, state='открыт', updated_by=?, updated_at=CURRENT_TIMESTAMP WHERE id=?`. Анкеты того периода (по `period_id`) все на месте | да, симметрично |

Кнопка «Открыть новый период» после закрытия остаётся — это осознанное создание следующего года. Кнопка «Открыть закрытый обратно» появляется рядом с ней (для случая «закрыли по ошибке, новый год ещё не нужен»).

## Изменения в коде

### 1. Схема и миграция (`src/db/schema.sql`, `src/db/migrate.js`)

- `schema.sql`: добавить `is_active INTEGER NOT NULL DEFAULT 0` в `CREATE TABLE periods`.
- `migrate.js` (идемпотентно, как остальное):
  ```
  const addedIsActive = await ensureColumn('periods', 'is_active', 'INTEGER NOT NULL DEFAULT 0');
  if (addedIsActive) {
    // существующий «текущий период» = самая новая строка → делаем её активной
    await run(`UPDATE periods SET is_active = 1
               WHERE id = (SELECT id FROM periods ORDER BY id DESC LIMIT 1)`);
  }
  // страховка от рассинхрона: если активной строки нет вообще — активировать новейшую
  await run(`UPDATE periods SET is_active = 1
             WHERE id = (SELECT id FROM periods ORDER BY id DESC LIMIT 1)
               AND NOT EXISTS (SELECT 1 FROM periods WHERE is_active = 1)`);
  ```

### 3. `apiSetPeriod` (`src/controllers/adminController.js:791`)

Разветвить по `action`:

- `action: 'close'` → `UPDATE ... SET state='закрыт' WHERE is_active=1`
- `action: 'reopen'` → `UPDATE ... SET state='открыт' WHERE is_active=1`
- `action: 'new'` (name обязателен) → `batch`: снять `is_active` со старого + `INSERT` нового с `is_active=1`
- `action: 'activate'` (id обязателен) → `batch`: снять `is_active` со старого + `UPDATE ... SET is_active=1, state='открыт' WHERE id=?`
  - валидация: строка с таким `id` существует; нельзя активировать уже активную (no-op с понятным ответом)

Каждое действие пишет `audit_log` с конкретной формулировкой (`период: закрыт` / `период: открыт заново` / `период: открыт новый "<имя>"` / `период: возвращён "<имя>" (#id)`).

Обратная совместимость: старый вызов `{ state: 'открыт'|'закрыт', name }` без `action` мапим — `state==='закрыт'` → close; `state==='открыт'` с новым `name` → new; `state==='открыт'` без имени → reopen. (Фронт всё равно переведём на `action`.)

`listPeriodGrants` (`GET /admin/period-grants`) уже возвращает `periods` с `surveysCount`, но с фильтром `WHERE p.id != (самый новый)`. Поменять на:

- `renderAdminPeriod` (~7631): когда период закрыт, показывать **две** кнопки — «Открыть новый период» и «Открыть закрытый обратно».

- API-обёртки в `app-core.js` (`apiSetPeriod` уже есть — расширить параметры; при необходимости `apiPeriodActivate`).

### 6. `deletePeriod` (`adminController.js:955`)

Guard `p.id != (самый новый)` → `p.is_active = 0` (нельзя удалить активный). Проверка «0 анкет» остаётся.

## Крайние случаи

- **Две вкладки / два админа одновременно.** Смена активного — атомарный `batch` (снять+поставить). Гонка «оба открывают новый» → просто два периода, активен последний; данные не портятся.
- **Активный период удалить нельзя** (guard). Пустой неактивный — можно.
- **Восстановление закрытого периода** всегда делает его `открыт` — это и есть намерение «продолжить работу». Отдельно «сделать активным, но закрытым» не нужно.
- **Совпадающие имена** больше не проблема: привязка и выбор — по `id`. В списке периодов показываем дату создания, чтобы различать.
- **Фолбэк в `getActivePeriod`**: если по какой-то причине активной строки нет — берём новейшую (старое поведение), не падаем.

## Оценка

Схема+миграция — маленькая. 14 call-sites — механически через общий хелпер. `setPeriod` — переписать одну функцию. Фронт — две правки в уже существующих функциях. Новых экранов нет. Split: 1 подготовка (схема/сервис/call-sites), 2 бэкенд-операции (setPeriod/activate/delete guard), 3 фронт, 4 проверка.
